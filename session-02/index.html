    What IR is — and what starts it

    IR exists so that when something goes wrong, you already know the steps. Five objectives in a fixed order, one responder at the front, and five ways an incident reaches you.

    What INE says

    Incident Response (IR) is the structured process organisations follow to detect, investigate, contain, eradicate, and recover from cybersecurity incidents, such as data breaches or malware infections.

    🎯 minimise damage⏱ reduce recovery time💰 reduce costs🛡 prevent future incidents
    Incident Response (IR)term
    Definition
    A structured, repeatable way to handle a security incident from the first signal to the lessons learned.
    Why it exists
    Attacks move in minutes. Improvised responses are slow, miss steps and destroy evidence. A structure removes guessing.
    Where used
    Every organisation that can be breached — which is every organisation. Regulators also require it.
    Example
    Ransomware on two PCs: isolate them, remove the malware, restore from backup, then find how it got in.
    SOC example
    At 03:00 the Tier 2 responder opens the ransomware playbook and follows it step by step — no meeting, no guessing.
    Quick checkPut the five IR objectives in orderThe ransomware night: drag or use the arrows, then Check.
    1. Detect — EDR flags files being encrypted on FIN-WS07
    2. Contain — isolate FIN-WS07 so it cannot spread
    3. Eradicate — remove the malware and its persistence
    4. Recover — restore the files from a clean backup
    5. Learn — find the root cause and close the gap
    The order matters. Eradicating before containing lets it spread while you clean; recovering before eradicating restores onto an infected system.
    The incident responder — the frontline defender

    INE: the professional who manages and handles security incidents.

    🔍 detect🧪 analyse🧱 contain♻️ recover📚 make sure we learn
    Words you will hear
    Incident handlingthe hands-on part of IR — many teams use it as a synonym
    Incident managementorganising the response: cases, tasks, people, records — a core function inside IR (Part 5)

    What starts an incident response?

    An incident rarely announces itself. It reaches the team through one of five doors — and your plan must list all five.

    TriggerExample at NovaCartPrepared means…
    SOC escalationTier 1 confirms a true positive and escalates to Tier 2A clear escalation path and severity levels
    Tool detectionThe EDR blocks a file and raises a high alertTools deployed, tuned and watched
    User reportf.nabil forwards a strange "payroll" emailEvery employee knows how to report
    Third partyA national CERT, a bank or the police callsA published contact and a call-back procedure
    Threat intelligenceA feed lists a domain NovaCart users visited yesterdayFeeds connected to the SIEM and the case platform
    Common mistake

    Only watching the SIEM. In many real cases the first signal is a person — a user, a customer or a partner. If nobody knows where to send that call, the clock runs and nobody starts it.

    Keep this

    Detect · Contain · Eradicate · Recover · Learn — in that order. If a step does not serve one of these five, it is not IR.

    Event, adverse event, incident

    Three words the exam uses exactly. Session 1 gave you event → alert → incident from the SOC side. Today you add NIST's middle word and the exact test for "incident".

    What INE says (from NIST SP 800-61r2)
    WordNIST definitionExample
    EventAny observable occurrence in a system or networka user logs in
    Adverse eventAn event with a negative consequencesystem crash · packet flood · unauthorised use of privileges · unauthorised access to sensitive data · malware that destroys data
    IncidentA violation or imminent threat of violation of computer security policies, acceptable use policies, or standard security practicesmany failed logins, then a success
    INE's events
    👤 a user logs in to a workstation📄 a file is opened or changed🧱 the firewall logs allowed traffic🔁 a scheduled reboot🛡 an AV scan completes
    INE's incidents
    🔑 many failed logins, then a success🦠 malware detected and quarantined📤 unusual outbound traffic from a server📂 unauthorised access to sensitive files⬆️ privilege escalation with no reason
    The incident test — three yes/no questions
    1Is a rule broken — or about to be? (security policy, acceptable use, standard practice)
    2Is C, I or A threatened? (confidentiality, integrity, availability)
    3One event or a series? 1 failed login = event · 300 failed + 1 success = incident
    ▶ Event, adverse event or incident?

    Decide first. Then click to check.

    Event

    Routine and expected. No negative consequence.

    Adverse event

    A negative consequence (a crash) — but no policy was violated and nobody attacked. IT fixes it; it is not a security incident.

    Incident

    Malware on an endpoint violates policy — even if it was quarantined. Someone must ask how it got there.

    Event

    Normal traffic, logged. It becomes interesting only with context — volume, destination, time.

    Incident

    Privilege escalation with no justification is a policy violation.

    Adverse event

    Availability was hurt, so it is adverse. But it was an accident, not a violation. If an attacker filled the disk on purpose, it would become an incident.

    Normal → event.

    Harm, no violation → adverse event.

    Policy violated → incident.

    Normal → event.

    No justification → incident.

    Harm by accident → adverse event.

    Common mistake — every alert is "an incident"
    alert = a signalvalidate itonly then: incident

    Wrong words → wrong escalation, wrong reports, wrong regulator deadlines.

    Why people get it wrong
    😨 fear of missing the breacheverything = "incident"alert fatiguethe real incident drowns
    Keep this

    Every incident is an event, but not every event is an incident. The test is a policy violation — or an imminent threat of one — against confidentiality, integrity or availability.

    Why every organisation needs IR

    Without a structured response capability, even a small incident can grow into a major breach with business, financial and reputational damage. INE gives four reasons.

    Reason 4 in numbers — the clocks regulators start

    Regulation turns "we will look into it" into a deadline. Legal must know these clocks before the incident — that is why legal sits in the IR plan.

    RuleWho it coversThe clock
    GDPR (EU) · Art. 33Anyone holding EU residents' personal dataTell the supervisory authority without undue delay, and where feasible within 72 hours of becoming aware of a personal-data breach
    NIS2 (EU) · Art. 23EU essential and important entitiesEarly warning in 24 h · incident notification in 72 h · final report within one month
    HIPAA (US) · Breach Notification RuleHealth providers, insurers, partnersNotify affected people without unreasonable delay — no later than 60 days
    PCI DSS · Requirement 12.10Anyone who stores or processes card dataAn incident response plan must exist, be tested and be ready to start at once
    What an unstructured response costs

    INE's list: delayed containment and recovery · more damage and downtime · poor communication and role confusion · missed compliance and reporting deadlines · no learning from past incidents.

    What IR buys

    INE: IR lets an organisation minimise damage, recover faster, meet compliance requirements, and build resilience against future attacks.

    Ask the room

    NovaCart's CFO asks: "Why should I pay for IR? We have never been hacked." Give one answer for each of INE's four reasons.

    Show one good answer

    Threat landscape: no organisation is immune — phishing and ransomware hit small shops too. Speed: an email can turn into stolen data in under an hour; we cannot plan in that hour. Business impact: one day of the shop offline costs a day of sales and customer trust. Regulation: we hold EU customer data — GDPR gives us 72 hours to report a breach; without a plan we will miss it. And: "never been hacked" may mean "never noticed".

    Keep this

    Threats grow · attacks are fast · downtime is expensive · regulators set clocks. Those four reasons are the business case for everything else today.

    Incident types vs attack vectors

    Two labels for every case. The type says what happened. The vector says how the attacker got in. The type picks the playbook; the vector picks the fix.

    Incident type = what happened

    Helps you classify the case, set its priority and open the right playbook.

    Attack vector = how it happened

    INE: the specific path, method or technique an attacker uses to gain unauthorised access to a system, network or application — "how an attacker gets in".

    1Phishing emailsT1566 Phishing

    Look forfake sender · link to a look-alike domain · "urgent" tone

    2Vulnerability exploitationT1190 Exploit Public-Facing App

    3Brute-force attacksT1110 Brute Force

    Look forhundreds of failed logins, then one success · a weak, reused password

    4Drive-by downloadsT1189 Drive-by Compromise

    A compromised or fake website downloads malware to the visitor.

    Look for"update your browser" pages · fake CAPTCHA that asks you to run a command

    5Supply chain attacksT1195 Supply Chain Compromise

    A trusted software or service provider is compromised — and you install its update.

    Look fora signed vendor update that suddenly calls an unknown server

    6Removable mediaT1091 Removable Media

    Malware on a USB drive or external disk.

    Look fora new USB device, then a program started from it (the picture in card 3 shows a USB attack tool)

    7Insider threatsT1078 Valid Accounts

    Malicious or negligent employees and contractors — the access is real.

    Look fornormal account, abnormal behaviour: odd hours, bulk downloads

    Why a framework — and NIST SP 800-61

    INE: a framework turns incident response from ad hoc firefighting into a disciplined, professional practice. NIST's is the global standard.

    What INE says — the goal of IR
    📉 minimise damage and disruption⏩ restore operations quickly🛡 reduce future risk⚖️ meet legal requirements

    "It's not just about reacting — it's about responding effectively, efficiently, and with purpose."

    What INE says — why NIST

    NIST SP 800-61 is the most widely adopted and recommended IR framework globally — chosen for its clarity, flexibility and comprehensive approach, and compatible with most other standards and tools.

    IR frameworkterm
    Definition
    A published, repeatable set of phases and activities for handling incidents.
    Why it exists
    Under pressure, people skip steps and argue about structure. A framework decides the structure in advance and gives legal, IT and the SOC one common language.
    Where used
    Inside the IR plan (section 4 is "IR process & procedures, based on NIST or SANS"), in playbooks, in audits.
    Example
    NovaCart's plan says: "We follow NIST SP 800-61r2." Every playbook step is tagged with its phase.
    SOC example
    The Tier 2 note says "Phase 3 — containment started 09:40". Legal knows exactly where the case stands without reading logs.
    ▶ Open each NIST phase

    Click a phase to see INE's key activities.

    • Develop an IR policy and define team roles
    • Establish communication plans and escalation processes
    • Deploy and configure security tools (SIEM, EDR, IDS/IPS)
    • Security awareness training for employees
    • Create and test playbooks for common scenarios
    • Threat modelling and risk assessments
    • Monitor security systems for alerts and suspicious activity

    5. Work the evidence. In the "check who clicked" task, log what the alert says about the proxy record: who visited the link, when, and whether a password was sent.
    6. Observables. Mark the sender address, domain, URL and IP as IOC. Do not mark the victim's own address as an IOC. If Cortex is available, run an analyzer on the domain and note the result in a comment.

    Respect PAP:AMBER — do not browse to the phishing URL; analyse it only through enrichment. Button names can differ slightly between TheHive versions — look for the same meaning.

    • Five tasks exist, and each closed task has a log.
    • At least four observables are marked IOC — and the victim's address is not.
    • T1566.002 is attached under Initial Access.
    • The case is closed as Resolved / True Positive with a summary.

    Five steps to build it (INE)

    1. Define the use case. Windows, Linux or cloud? A field kit (USB / live boot) or a dedicated IR workstation?
    2. Pick core capabilities. Collection, memory, logs — aligned with your plan and playbooks.
    3. Select and test. Reliable, well-supported tools (open source or vendor-approved); test in a sandbox first; write a quick reference.
    4. Package and organise. A clear folder structure — a USB with write blockers, a preloaded VM image, or a cloud kit for cloud incidents.
    5. Maintain. Keep tools current; review after new attack trends, lessons learned and team feedback.
