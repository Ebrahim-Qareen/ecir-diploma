    Web Application & Insider Threat — Reading the Application Layer

    Session 8 taught you to read packets. But your company's front door is not a port — it is a login page, and it is open to the entire internet on purpose.     Why this session matters for your job

    A firewall rule can close a port. Nothing can close port 443 on your public web server — the business needs it open. That makes the web application the one attack surface you can never remove, only watch. And the insider is the mirror image of the same problem: you cannot revoke access from someone whose job requires it. Both cases are won the same way — by knowing what normal looks like well enough to see the moment it stops.

    The four tiers, and who attacks which

    The attacker's view — why they start here

    To attack your endpoints, an attacker needs a phish to land or a user to click. To attack your web application they need nothing but the URL. No social engineering, no malware, no delivery problem — the target is publicly addressable, it answers on demand, and it is often running code written years ago by someone who has left the company.

    And the attack traffic looks exactly like real traffic, because it is real traffic. That is what makes web attacks "stealthy in nature" — Maharah's phrase — and it is why detection here is about payload content and response codes, not about connections.

    Key takeaway

    You cannot close the front door. You can only make sure that every person who walks through it is written down — which is why logging is a security control, not an operations chore.

    OWASP Top 10 — The Analyst's Map

    You are not being asked to memorise a list. You are being given a shared vocabulary, so that when you write "T1190 — injection" in a ticket, everyone knows exactly what you mean.

    The OWASP Top 10 is a risk list for developers. As an analyst you read it backwards: for each risk, ask "what would this look like in my logs?" Some are loud, some are silent — and knowing which is which is the actual skill.

    #OWASP 2017 riskWhat it looks like to youLog-visible?

    2Broken AuthenticationBurst of failed logins then one success; session IDs appearing in URLs.✅ loud

    The 2021 regrouping — know that it exists

    OWASP reorganised the list in 2021. Injection absorbed XSS; Broken Access Control moved to #1; and three new categories appeared: Insecure Design, Software & Data Integrity Failures (which now contains deserialization) and Server-Side Request Forgery. Insufficient Logging was renamed Security Logging & Monitoring Failures and stayed in the list.

    Why we still teach the 2017 numbering here: it is the version the Maharah CH05 material and most incident-handling curricula use, and its ten categories map more cleanly onto ten distinct log signatures. Learn the 2017 list for the exam; know the 2021 names so you are not lost in a real meeting.

    Risk #10 is the one that ends careers

    "Web applications maintain logs to track usage patterns… when logging and monitoring is insufficient, attackers operate undetected for extended periods." Every other risk on this list is survivable if you see it happen. Without logging, the first nine are all the same incident: the one you found out about from a customer, six months late.

    Key takeaway

    Read OWASP as a detection checklist, not a developer checklist. Three of the ten are effectively invisible in a raw access log — access control, deserialization and XXE — and those are precisely the ones where you must correlate the web log with the application and endpoint logs to see anything at all.

    The trap that catches every new analyst

    A login brute force is POST traffic. The access log will show you a hundred POST /login.php lines with status 200 and tell you nothing about which credentials were tried or whether any worked — because the username and password are in the body, and the body is not logged.

    To answer "did they get in?" you need one of: the application log (which logs the authentication result), the WAF log (which sees the body), or a PCAP. This is exactly the pivot the TryHackMe Detecting Web Attacks room makes when it moves from Task 4 (logs) to Task 5 (packet capture) — and it is the single most useful habit in this whole session.

    Preparation — what Maharah tells you to have ready before the incident

    A ready-to-use backup website; an IP/protocol allowlist; low DNS TTLs on critical records so you can fail over quickly during defacement or DDoS; monitoring tools deployed; and regular audit of web server logs and settings. Notice that three of those five are about being able to move fast later, not about stopping the attack.

    Key takeaway

    Ask the question first, then choose the evidence. "What did they try?" → access log. "What broke?" → error log. "Was it blocked?" → WAF log. "Which user, which record?" → application log. "Did the database actually run it?" → DB log. "What exactly was in the body?" → PCAP.

    Reading a Log Line, Field by Field

    One line. Nine fields. Learn them once and every web investigation for the rest of your career gets faster.

    ▸tail -f /var/log/apache2/access.logApache combined format
    203.0.113.44 - - [12/Aug/2026:09:41:07 +0000] "GET /index.php HTTP/1.1" 200 4821 "https://shop.itgate.local/" "Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/128.0"
    1 · 203.0.113.44 client IP — but if you sit behind a proxy or CDN this is the proxy's IP; the real client is in X-Forwarded-For. Check this before you block anything.
    2 · - - identd and HTTP auth user. Almost always empty; when the second one is populated it is gold, because it names the account.
    3 · [12/Aug/2026:09:41:07 +0000] timestamp with offset. Note the offset — your Wazuh timeline is probably in UTC and your firewall may not be.
    4 · "GET /index.php HTTP/1.1" the request line: method, path and query string, protocol. This is where GET-based payloads live.
    5 · 200 status code — the single most important field on this page.
    6 · 4821 response size in bytes. A sudden 40× jump on a normal-looking URL is a data dump.
    7 · "https://shop.itgate.local/" referer — attacker-controlled, so treat as a claim, not a fact.
    8 · "Mozilla/5.0 …" User-Agent — also attacker-controlled, but tools frequently forget to change it. That is how you find FFUF, Hydra, sqlmap and Nikto for free.

    Status codes as a story

    CodeMeansWhat it tells the analyst
    200OKThe server did what was asked. After a burst of 404s or 401s, this is the breach.
    301 / 302RedirectOften the login flow. A redirect away from a login POST usually means success.
    401 / 403Unauthorised / ForbiddenAccess control is working. Hundreds in a row = someone testing it.
    404Not foundOne is a typo. Six hundred in ninety seconds is directory fuzzing.
    500Server errorThe application crashed on the input it was given — a very strong injection signal.
    503Service unavailableThe server is overloaded. In volume, this is your DoS indicator.
    Key takeaway

    Two fields carry most of the weight: the request line (what they sent) and the status code (what the server said back). Everything else is context. Read them as a pair, in time order, and the attack tells you its own story.

    S09 · P08Method⏱ 12 min

    The Six-Step Web Log Method

    The same discipline as Session 8's packet method, adapted to logs. Do it in order, every time, and you will never improvise under pressure.

    1. Shape the data. Before filtering anything: count requests per IP, per status code, per URI. The outliers announce themselves — one IP with 40× everyone else's request count, or an endpoint with an unexplained wall of 404s.
    2. Confirm the alert. Filter to the reported IP or URI. Does the traffic match what the WAF or Wazuh rule claimed? If it does not, you may have a broken rule — which is also a finding worth writing down.
    3. Name the attack. Match the payload against the signature tables you will build over the next ten pages. Record the exact string, decoded, and the exact query that isolated it.
    4. Answer the only question that matters: did it work? Look at the status code and the response size for the attack requests. 404/403/500 = attempts. A 200 with an unusual size = you now have an incident.
    5. Look for the next stage. Attackers do not stop at one technique. From the same source IP, search for an upload, a new file being requested, an outbound connection from the web server, or a new account. This is the step that turns a ticket into a breach.
    6. Identify the actor and the blast radius. Correlate the web log with the application log (which user session?), the endpoint (which process did the web server spawn?) and the firewall (where did the data go?). Now you can name the target, the account and the damage.
    Automated vs manual detection — and when you fall back to manual

    Automated means the WAF, IDS or SIEM raised the alert for you. Manual means no appliance fired, but you have strong evidence of compromise anyway — a defaced page, a customer report, a strange outbound connection — and you must go read the raw logs yourself.

    Manual detection is slow and it is the real job. It means searching large log files for the characters that indicate an attack, which is exactly what the next ten pages teach you to do.

    Key takeaway

    Shape → confirm → name → did it work? → next stage → who and how far. Steps 4 and 5 are the ones inexperienced analysts skip, and they are the two that decide whether you close a ticket or declare an incident.

    S09 · P09Defence⏱ 20 min

    The WAF — and How Attackers Encode Around It

    A firewall filters by address and port. A WAF filters by meaning — and meaning can be spelled a lot of different ways.

    A Web Application Firewall sits at the edge and inspects complete web requests — headers, URL, query string and body — deciding whether to allow or block each one against a ruleset. Unlike Wireshark it can decrypt TLS first, so it sees the plaintext request before the server does. Its weakness is that it matches patterns, and the same payload can be written many ways.

    Encoding evasion simulator — one payload, four spellings, one naive rule
    Payload
    Plain payload. The rule looks for the literal string <script> and it is right there, so the request is blocked. This is the only case a naive string-match rule handles correctly.
    SpellingTechniqueNaive rule
    <script>alert("XSS")</script>Plain text✅ blocked
    <sCRipT>alert("XSS")</ScRiPt>Toggle case❌ missed
    %3cscript%3ealert("XSS")%3c/script%3eURL / hex encoding❌ missed
    %253cscript%253ealert(1)%253c/script%253eDouble encoding❌ missed

    All four produce the same result in the browser. Double encoding (%25 is an encoded %) is designed specifically to survive one round of URL-decoding — the WAF decodes once, sees harmless text, and passes it to a server that decodes again.

    Red flags — investigate these in your WAF and access logs
    • The same client IP appearing repeatedly with different encodings of the same payload — that is deliberate rule-probing, not a scanner
    • %25 anywhere in a query string — legitimate applications almost never double-encode
    • A WAF rule in "detect only" mode firing hundreds of times and blocking nothing
    • A burst of blocks from one IP that stops abruptly — they either gave up or found the way through; assume the second
    • Requests that the WAF allowed but the error log shows crashed the application
    🔬 Build one yourself — TryHackMe "Detecting Web Attacks", Task 6

    The room's final task gives you a simple WAF rule builder. You are asked to block a specific scanner by its User-Agent, and the rule you construct is literally IF User-Agent CONTAINS "BotTHM" THEN block — condition, operator, value, action. That four-part shape is the same in ModSecurity, AWS WAF and Cloudflare; only the syntax changes.

    What to practise: after building the rule, ask yourself how you would evade it. Changing one character of the User-Agent defeats it entirely — which is exactly why real rulesets match on behaviour and payload, not on a name the attacker chooses.

    Reconnaissance and Directory Fuzzing

    Before anyone attacks your application they have to find out what it is made of — and the only way to do that from outside is to ask for thousands of things that do not exist.

    Directory fuzzing means firing a wordlist of paths at the server and keeping whatever answers. Tools like ffuf, gobuster, dirb and Nikto do this at hundreds of requests a second. In an access log it is unmistakable: one client IP, a solid wall of 404, and then — the part that matters — a handful of 200s that tell the attacker where to go next.

    What you needQuery / filter

    The paths that did existclientip="203.0.113.44" status=200 | table _time uri status bytes
    Rate — requests per minute from one source| bin _time span=1m | stats count by clientip _time | where count > 100
    Red flags — investigate these in your access log
    • Hundreds of 404s from one source IP inside a couple of minutes
    • A scanner name left in the User-Agent — ffuf, gobuster, Nikto, sqlmap, Nmap Scripting Engine
    • Requests for paths that only an attacker would guess: /admin, /.git/, /backup.zip, /wp-login.php, /phpinfo.php
    • An alphabetical or wordlist-ordered sequence of paths — humans do not browse in alphabetical order
    • The 200s inside the 404 storm — those are the pages the attacker just discovered. Go look at what they did with them next.

    S09 · P11Attack 2 · Injection⏱ 22 min

    SQL Injection — The One That Empties the Database

    Untrusted input reaching the database as code. Old, extremely well understood, and still responsible for a large share of the breaches you will read about this year.

    The application builds a query by pasting user input into a string. The attacker sends input that ends the intended query and starts their own. Because the database has no idea a human was involved, it simply obeys. In the logs, SQLi is loud — the payload has to travel in a parameter, and parameters are logged.

    ▸grep -Ei "(' or |union select|xp_cmdshell|--|sleep\()" /var/log/apache2/access.logmanual SQLi hunt
    12:34:35 192.2.3.4 GET /login.asp?username=blah' or 1=1 -- HTTP/1.1 200 8140
    12:34:36 192.2.3.4 GET /login.asp?username=blah' or ) 1=1 (-- HTTP/1.1 500 412
    12:34:41 192.2.3.4 GET /login.asp?username=blah' or exec master..xp_cmdshell 'net user test testpass'-- HTTP/1.1 200 190
    Three requests, three lessons. Line 1: the classic always-true condition, and the 200 with a large response says it worked. Line 2: a malformed attempt — the 500 is the database throwing a syntax error, which is itself proof the input reaches the query. Line 3 is the dangerous one: xp_cmdshell is not a data query at all, it is remote code execution — this request creates a local user account on the database server.

    S09 · P12Attack 3 · Client-side⏱ 18 min

    Cross-Site Scripting — Attacking Your Users Through You

    In SQLi the victim is your database. In XSS the victim is your customer, the weapon is your website, and the first person to notice is usually them.

    XSS injects client-side script into pages that other people view. Reflected XSS bounces the payload straight back in the response and must be delivered per-victim, usually by a link. Stored XSS is saved in your database and fires for every visitor — far more serious. DOM-based XSS never reaches the server at all, which means your access log will show nothing.

    Signature in the logNotes
    <script · </script>The obvious form — and the one every WAF already blocks
    %3cscript%3e · %253cscriptURL and double URL encoding — decode before you judge
    onerror= · onload= · onmouseover=Event handlers — no <script> tag needed at all
    javascript: · <img src=x · <svgAlternative injection vectors that bypass naive tag filters
    document.cookie · fetch( · new Image().src=The payload's purpose — stealing the session and sending it out
    A request to an external host carrying a long tokenThe cookie leaving. This is the part that actually hurts.
    Red flags — investigate these in your access and WAF logs
    • Any HTML or JavaScript syntax in a parameter — and its encoded variants, especially %3c and %253c

    • A payload sent to a form that stores data (comment, profile, review) rather than a search box — that is stored XSS, and the blast radius is every visitor

    Path Traversal and Local File Inclusion

    The application was told to open a file whose name came from the user. The user chose a name outside the web root.

    Any parameter that names a file — ?page=, ?file=, ?template=, ?lang=, ?download= — is a candidate. Adding ../ walks up the directory tree until the attacker reaches something valuable: /etc/passwd, a config file with database credentials, an SSH key, or on Windows the SAM hive. Because it travels in the URL, path traversal is fully visible in the access log.

    Command Injection and SSRF

    Two different bugs with the same consequence: your web server starts doing things on the attacker's behalf, from inside your network.

    Command injection happens when user input is passed to a shell — the attacker appends ;, | or && and their own command runs as the web server user. SSRF makes the server fetch a URL the attacker chooses, turning it into a proxy into your internal network — including cloud metadata services that hand out credentials to anything that asks.

    A suspicious string in a URL is a hypothesis. The proof is on the endpoint: Apache or Nginx is not supposed to have child processes.     • A parameter containing a URL, especially one pointing at 127.0.0.1, localhost, a private range, or 169.254.169.254
    • The web server process spawning a child process — there is almost never a benign explanation
    • Outbound connections from the web server to an address it has never contacted, minutes after a suspicious request
    • A new file appearing under the web root, or a cron/scheduled task created by the web server account

    Malicious Upload and the Web Shell

    The attacker's goal is not to break in once. It is to leave a door that looks like part of your website.

    A web shell is a small script — .php, .jsp, .aspx — placed inside your web root that runs whatever command it is sent. It needs no malware, no C2 implant, no persistence mechanism: it is the persistence, and it is served by your own web server over your own port 443. This is why it survives reboots, endpoint scans and firewall rules.

    Broken Access Control and IDOR

    The hardest attack on this list to detect, because every single request is perfectly valid and the server answers every one of them with 200 OK.

    Insecure Direct Object Reference means the application checks that you are logged in, but never checks that the record you asked for is yours. The attacker changes ?invoice_id=1041 to 1042 and reads someone else's data. No payload, no strange characters, no error — which is exactly why signature-based detection is useless here and behavioural detection is the only option.

    The access log records the URL and the status. It does not record which user was authenticated for that request.     The Insider — When the Attacker Already Has a Badge

    The answer to the break question is none of them. Every detection you built this morning assumes the attacker is trying to get in. The insider is already inside.

    An insider is a trusted person with access to the organisation's critical assets: privileged users and IT staff, disgruntled employees, terminated employees whose accounts were never deprovisioned, third-party contractors and vendors, and undertrained staff who cause damage without meaning to.

    TypeWhat they doHow you respond
    MaliciousDeliberately steals data, sabotages systems, or acts for personal gainFull investigation with HR and legal from day one
    NegligentWeak passwords, clicked the phish, emailed a file to the wrong addressTraining and control changes — not a disciplinary case
    ProfessionalRecruited or planted by an external actor to steal from withinCounter-intelligence posture; assume they know you are watching
    CompromisedA legitimate user whose credentials or device an outsider now controlsTreat as an external breach wearing their identity
    The distinction that changes everything you do next

    A compromised insider is a technical incident: reset the credentials, reimage the device, hunt the intruder. A malicious insider is a personnel and legal matter that happens to have technical evidence — and if you treat it as a normal incident, you will destroy that evidence in the first ten minutes by resetting the account and wiping the laptop.

    You often cannot tell which one you have at the start. So the rule is: when an insider is suspected, preserve first and remediate second — and tell your manager before you touch anything.

    Why the perimeter never helps

    MITRE calls this T1078 — Valid Accounts, and the reason it is so effective is that nothing is technically wrong. The login succeeds. The file access is permitted. The VPN session is legitimate. There is no malware to detect, no exploit to signature, no unusual port. Every control you have built so far in this course is looking for something that will not happen.

    Which leaves exactly one signal: this is not what this person normally does. That is the whole of insider detection, and it is why the next page is about baselines.

    Key takeaway

    Four types, two response paths. Ask early: is this person acting, or is someone acting as them? Your answer determines whether the next call is to IT or to HR — and whether your first action is a password reset or a forensic image.

    Detecting the Insider — Baselines, UBA and Canary Data

    You cannot detect "wrong". You can only detect different — which means you have to know what normal looks like first.

    Three techniques, in increasing order of how uncomfortable they make people. Behavioural profiling builds a pattern of normality for an individual and flags departures from it. User Behaviour Analytics (UBA) does the same automatically at scale, scoring unusual file access, data volume and login patterns. Mole detection is different in kind: you plant unique data with different people and see whose copy surfaces.

    Mole detection — the canary token

    Give a slightly different version of the same sensitive item to each suspect: a watermarked document, a unique URL, a fake customer record with a distinctive name, a figure that differs in the last digit. When the information reaches the public — or a competitor — the variant that leaked names the person who leaked it.

    Cheap, effective, and completely useless if you deploy it after the leak. Like most of insider defence, this is a preparation control.

    Red flags — investigate these across your auth, file and network logs
    • Access to systems or file shares the person has never touched before, especially outside their department
    • A gap in a log source that should be continuous — missing or truncated logs are an act, not an accident
    • Authentication at 02:00 from an account that has only ever worked 09:00–17:00
    • A sharp rise in volume of records read by one account with no matching business event
    • Activity spiking in the two weeks after a resignation, a poor review, or a passed-over promotion — the highest-risk window there is

    Insider Exfiltration — In the Logs and On the Wire

    The theft itself is usually the least sophisticated part. It is also the last moment you can still stop it.

    Insiders rarely need clever exfiltration, because nothing is blocking them.     Same rule, same payload, same attacker. The response decides the severity. Do not wait for your analysis to raise it.

    The three questions that decide whether this is real

    The SIEM query that answers question 3 
    index=web src_ip="203.0.113.44" earliest=-24h
| stats count AS requests
        dc(uri_path) AS endpoints_touched
        values(status) AS status_codes
        max(bytes) AS largest_response
        min(_time) AS first_seen
        max(_time) AS last_seen
        by src_ip useragent
| eval duration_min = round((last_seen - first_seen)/60, 1)

Blocking only one IP and declaring victory — attackers have more than one IP.

    Neutralise, isolate, preserve. Then remediate.

    Insider containment is different — and it is not your decision

    For a suspected malicious insider, containment means blocking all access at once — email, applications, VPN, network credentials and the physical access card — seizing the issued devices, restricting site access, and notifying the affected department so they can assess losses.

    None of that is a SOC decision. Device seizure, and especially anything involving a personal device, needs HR and legal authorisation and a documented chain of custody. Your job is to preserve evidence and brief accurately; the decision to act belongs to management.

    Key takeaway

    Block the source, filter the payload, and be ready to fail over to the backup site. Neutralise the shell without deleting it. And for insiders, remember that the technical containment is the easy half — the hard half is legal, and it is not yours to authorise.

    S09 · P30Tier 2 · Recover⏱ 18 min

    Eradication and Recovery

    Containment stops today's attack. Eradication makes sure the same request fails tomorrow — at every layer it passed through.

    Eradication for web incidents is a defence-in-depth checklist. The same malicious request crossed five components on its way in; fix it at every one, because the fix at any single layer will eventually be bypassed.

    LayerEradication action
    Input / login formServer-side input validation and allowlisting. Never rely on client-side checks.
    WAF / IDSMove the rule from detect-only to blocking; add rules for the encoded variants, not just the literal payload.
    FirewallRestrict inbound to the ports actually needed; restrict egress so a shell cannot call home.
    Web serverPatch. Disable unused modules and ports. Deny script execution in upload directories. Turn off directory listing.
    Source codeFix the vulnerable query — parameterised statements / prepared statements. Sanitise and encode output. Review for the same pattern elsewhere.
    Third-party componentsUpdate the vulnerable library; minimise dependencies; maintain the SBOM so next time you can answer "do we run it?" in minutes.
    Error handlingCustom error pages. No stack traces, no SQL messages, no framework versions returned to users.
    DatabaseApplication connects with a non-privileged account; least privilege on tables and columns; use stored procedures; disable dangerous procedures such as xp_cmdshell.
    Operating systemPatch, harden, and confirm the web server account cannot write to the web root.
    Recovery — six steps, in order
    1. Identify and patch the specific vulnerability that was exploited. If you cannot name it, you have not finished the investigation.
    2. Scan every web resource — servers and databases — for malware and leftover attacker artefacts, and remove them.
    3. Restore from a clean, verified, patched backup. Verified means you checked it predates the compromise.
    4. Confirm the application recovered completely: user accounts, privileges and configuration all as they should be.
    5. Restore databases from trusted backups where data was modified or destroyed.
    6. Define access control rules — an access control matrix listing which requests are authorised for which roles.

    Then run a vulnerability scan (OWASP ZAP, Nikto, Burp) against the restored application to prove the hole is closed, and watch the WAF and SIEM for the same pattern returning. It usually does, within days.

    Insider eradication — five controls

    Access control (review and revoke excessive permissions, enforce RBAC) · data encryption at rest and in transit to limit what exfiltration is worth · storage isolation for critical data · password rotation across affected and related accounts, with MFA · and PAM — privileged access management to monitor, record and control privileged sessions.

    Of those five, PAM is the single most impactful control against insider privilege abuse, because it turns "an admin did something" into "an admin did this exact thing, and here is the recording".

    Key takeaway

    Eradication is not "we deleted the shell". It is a fix at every layer the request crossed, and it is not complete until you can point to the code change. Recovery is not complete until a scan proves the vulnerability is gone.

    Insider forensics has a dimension no other incident type has

    Insider cases end in employment tribunals and, sometimes, criminal court. That means the first recovery step is not "restore service" — it is gather evidence to a standard admissible in a court of law: forensic imaging, hashing, write-blocking, and an unbroken chain of custody for every device.

    It also means you stop earlier than you would otherwise. Reading a colleague's personal files, or touching a personal device, without HR and legal authorisation can destroy the case and expose you personally. When you suspect a malicious insider, your next action is a phone call, not a command.

    Building the timeline
    • Normalise every clock to UTC first. Apache writes an offset, MariaDB may not, and the firewall is on its own NTP. A 40-second skew will make you chase a ghost.
    • Anchor on the first malicious request, not the alert. The alert is when you noticed; the first request is when it started, and the gap between them is your detection deficit — report it.
    • One row per event, with the evidence reference on every row. "14:18:57 — ext.php written by www-data (auditd, CASE-2609-audit.txt line 402)."
    • Mark what you inferred versus what you observed. "Attacker likely read the customer table" is an inference; "response was 148 KB against a 4 KB baseline" is an observation. Keep them visually separate.
    Key takeaway

    Collect fragile before durable, hash before you read, and never analyse the original. In web cases the decisive comparison is shipped log versus local log. In insider cases the decisive question is who authorised you to look at this — ask it before you run the command, not after.

    S09 · P33Hands-on⏱ 25 min

    Guided Lab — Attack, Detect, Respond

    Instructor drives the attack from KALI-ATK01 on the projector; you drive the detection on your own analyst workstation.

    1. Baseline first (5 min). Before any attack, run tail -f /var/log/apache2/access.log and browse the lab portal normally. Note the status codes, the response sizes and the User-Agent. You cannot call anything abnormal until you have seen normal.
    2. Recon (3 min). Instructor runs a directory fuzz. You find it: count 404s per client IP, extract the User-Agent, then list the 200s. Write down what the attacker just learned.
    3. Injection (5 min). Instructor sends a series of SQLi payloads, some URL-encoded. You grep for the signatures, decode every hit in CyberChef, and check the MariaDB error log for the syntax-error burst.
    4. Did it work? (4 min). Find the request whose response size is far above the baseline. This is the moment the exercise stops being a drill — say "confirmed breach" out loud when you find it.
    5. Web shell (5 min). Instructor uploads a shell and runs two commands. You find the POST, the new file's first GET, and confirm the write with ausearch -f /var/www/html/uploads. Hash the file. Do not delete it.
    6. Contain (3 min). Add the FortiGate block for the source, switch the WAF profile to blocking, and disable script execution in the upload directory. Verify by replaying one attack request and watching it fail.
    Verification step — do not skip this

    You have not finished until you can state, from evidence and without guessing: the attacker's IP, the vulnerable endpoint, the decoded payload, the exact timestamp the injection first succeeded, the path and SHA-256 of the web shell, and the destination of the outbound connection. Six facts. If you are missing one, go back and find it before the next page.

    Q6 Discussion: the room ends by having you build a WAF rule blocking a specific User-Agent. Would that rule have stopped any of the four attacks you just investigated?

    Reveal the answer

    Only by accident, and only until the attacker changed one character. The fuzzing, the brute force and the SQLi are all defined by their payload and volume, not by the name the tool reports. A User-Agent rule would have blocked the fuzzing run in this specific lab because the attacker left FFUF v2.1.0 in place — but that is the attacker's mistake, not your control.

    Rules that would actually have worked: a rate threshold on 404s per source IP; a threshold on POSTs to login.php per source; and a payload rule for SQL metacharacters in parameters, applied after URL-decoding. That is the difference between a signature and a detection.
