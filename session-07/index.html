    S07 · P04Why it matters⏱ 15 min

    Why Phishing Still Wins

    Every control we have ever built, and one well-written sentence still walks past all of them — because it attacks the person, not the machine.

    #1initial-access vector for intrusions, year after year
    ~1 in 3users will click a convincing lure without training
    minutesfrom click to stolen credentials being used

    The attacker's advantage

    A firewall must be right every time. A user must be right every time. But the attacker only has to be convincing once, to one person, on a busy afternoon. That asymmetry is why phishing has survived every generation of security technology.

    Why it works on smart people — the psychology

    Phishing does not target ignorance, it targets normal human wiring:

    • Authority — the message appears to come from IT, the CEO, the bank. We are trained to comply with authority.
    • Urgency — "your account will be locked in 24 hours." Urgency shuts down slow, careful thinking.
    • Fear of loss — an unauthorised charge, a suspended account. Loss motivates faster than gain.
    • Curiosity — "here is the invoice", "see the attached resume." We are wired to look.
    • Habit — a person who opens 80 emails a day is on autopilot. Autopilot does not check headers.

    The technical controls we build in this session exist because awareness alone will always fail sometimes.

    Where email sits in the attack — the Cyber Kill Chain

    The Lockheed Martin Cyber Kill Chain breaks a targeted attack into seven stages. Its value is simple: break any single link and the attack stops. Email is almost always stage 3 — Delivery — which makes it the earliest, cheapest place to break the chain.

    What this means for an L1 analyst

    Two things follow. First, never blame the user who clicked — if you do, the next person will hide it instead of reporting it, and your detection time goes from minutes to weeks. Second, a reported email is a gift: someone gave you the attack before it succeeded — the chain was broken at stage 3, exactly where it is cheapest to break. Treat every report as valuable, even the false alarms.

    What changed recently

    AI removed the typos. The old advice — "look for bad grammar" — is now the weakest indicator we have. Modern lures are fluent, correctly branded, and often reference real context stolen from a previous breach. This is precisely why we move the analysis from how it reads to what the headers and infrastructure prove. The rest of this session is that shift.

    S07 · P05Theory⏱ 12 min

    What an Email Actually Is

    Before you can judge an email, you have to know what one is made of. It starts with the oldest piece of the internet still in daily use — the address.

    Email as we know it was popularised on ARPANET in the 1970s by Ray Tomlinson, who chose the @ symbol to separate who from where. That decision is still the foundation of every address you will ever investigate.

    Anatomy of an email address

    Analogy. An email address works exactly like a postal address. The domain is the apartment building — it tells the postal service which building to drive to. The username is the specific mailbox inside the lobby. Give a postal worker both and the letter arrives. And just like the post, anyone can write any name on the envelope — that is the whole problem we spend today solving.

    The look-alike trick you must be able to see

    Attackers register domains that survive a fast glance:

    • Typosquatting — micros0ft.com (zero for "o"), tryhatme.com, paypa1.com.
    • Extra words — paypal-security.com, microsoft-login.net. The real brand is there, but it is not the registered domain.
    • Subdomain deception — paypal.com.verify-account.ru. Read a domain right to left: the real owner here is verify-account.ru.
    • Display-name spoofing — the name says Netflix Billing, the address is gibberish@sultanbogor.com. The display name is free text and proves nothing.
    Analyst habit to build today

    When you see a sender, do not read the display name — read the domain, right to left, one character at a time. It takes three seconds and it catches most of what reaches an inbox.

    S07 · P06Theory⏱ 15 min

    How an Email Travels — SMTP, POP3, IMAP

    Three protocols do all the work. Knowing which one does what tells you where the evidence lives when you have to go looking for it.

    ProtocolJobDirectionDefault ports
    SMTP
    Simple Mail Transfer Protocol    		Sends email — client→server and server→serverOutbound25 (relay), 587 (submission), 465 (implicit TLS)
    POP3
    Post Office Protocol v3    		Downloads email to one deviceInbound110, 995 (TLS)
    IMAP
    Internet Message Access Protocol    		Syncs email across many devicesInbound143, 993 (TLS)
    POP3 — download and go
    • Mail is downloaded and stored on a single device.
    • Sent messages live only on the device that sent them.
    • Typically removed from the server after download.

    Forensic consequence: if the user's mailbox is POP3, the server copy may already be gone — the evidence is on the endpoint, and you must preserve it before anything else touches that machine.

    IMAP — the server is the truth
    • Mail stays on the server and syncs to many devices.
    • Sent messages are stored server-side.
    • Deleted only when the user explicitly deletes.

    Forensic consequence: the server holds the authoritative copy. You can pull the original message and search every other mailbox for the same campaign — this is what makes blast-radius work possible.

    The journey of one message

    1. User sends. The mail client hands the message to its own mail server using SMTP.
    2. DNS lookup. The sending server asks DNS: "which server receives mail for this domain?" (the MX record).
    3. DNS responds with the address of the recipient's mail server.
    4. Delivery. The message crosses the internet server-to-server, again over SMTP.
    5. Checks run. The receiving server verifies SPF, DKIM and DMARC, then filters spam and malware.
    6. Retrieval. The recipient's client collects it with POP3 (download) or IMAP (sync).
    The one thing to remember

    SMTP was designed to be trusting. It happily accepts whatever "From" address the sender types — there is no built-in identity check at all. SPF, DKIM and DMARC (P09) were bolted on decades later precisely to fix that hole. Every phishing email you ever analyse exploits that original design decision.

    S07 · P07Evidence⏱ 18 min

    Email Headers — Where the Evidence Lives

    The body is written by the attacker. Most of the header is written by the servers. That is why headers are evidence and the body is only a story.

    Every email has exactly two parts: the header (metadata — who, when, via which servers) and the body (the message the human reads). Your mail client shows you five friendly header fields. The raw source shows you thirty, and the interesting ones are never in the friendly five.

    The headers a user sees

    HeaderWhat it meansCan the attacker set it?
    FromThe claimed sender addressYes — freely forged
    ToThe recipientYes
    SubjectSubject lineYes
    DateWhen it was sentYes
    Reply-ToWhere replies go — optionalYes — and this is often the real tell
    The Reply-To trick

    A classic business-email-compromise pattern: From: ceo@yourcompany.com but Reply-To: ceo.yourcompany@gmail.com. The mail looks internal, but the moment the victim replies, the conversation leaves your organisation entirely. Always compare From and Reply-To.

    The headers only the raw source shows

    HeaderWhy an analyst cares
    Received:The hop-by-hop travel history. Your single best evidence.
    Return-Path:The real envelope sender — where bounces go. Often differs from From.
    Authentication-Results:The receiving server's SPF / DKIM / DMARC verdicts.
    Message-ID:Unique ID — use it to find this exact message in server logs.
    X-Originating-IP:Where the message was actually composed (when present).
    X-Mailer: / User-AgentThe sending software — bulk mailers and scripts leave fingerprints here.
    Content-Type:Plain text, HTML, or multipart with attachments.

    Reading the Received: chain

    The forged-hop test — do this every time 
    Received: from example.org ([104.128.23.115])
    by mail.target.com (8.8.5) ...

    The sending machine announced itself as example.org in the SMTP HELO/EHLO greeting. But the receiving server also recorded the real TCP source IP in brackets — and that it cannot be faked. Look up the IP: if 104.128.23.115 actually belongs to xsecurity.com, the greeting was a lie.

    Rule: compare the announced name to the bracketed IP. A mismatch is a high-confidence spoofing indicator — and it is one of the few things in an email that an attacker cannot control.

    How to get the raw source

    ClientPath
    GmailOpen message → ⋮ (More) → Show original
    Yahoo MailOpen message → ⋯ (More) → View raw message
    Outlook (desktop)File → Properties → Internet headers
    ThunderbirdView → Message Source — or Ctrl+U
    In our lab

    Thunderbird is installed on the analyst workstation for exactly this reason. Ctrl+U on any .eml gives you the full raw source in one keystroke — headers, body, and the base64 of every attachment. That single shortcut is the start of every investigation today.

    S07 · P08Evidence⏱ 15 min

    The Body, MIME & Attachments

    The body is where the attacker does their persuading — and where the payload hides. MIME is the structure that carries both.

    An email body is either plain text or HTML. HTML brings images, styling and links — which is exactly why phishing lives there. And when there is an attachment, the whole message becomes multipart MIME: several parts glued together in one text file.

    What a message with an attachment really looks like

    Why base64, and what it means for you

    SMTP was built for plain text, so binary files must be converted to safe text before travelling. That is base64. The practical consequence for an analyst is excellent: the attachment is right there in the raw source, as text. You can extract and decode it — with CyberChef or a base64 decoder — and rebuild the exact file without ever opening the email in a mail client. That is the safest possible way to get your hands on a suspicious attachment.

    Reading links safely

    In HTML, the text you see and the destination you go to are two different things:

    <a href="http://evil-domain.ru/harvest.php">https://www.paypal.com/account</a>
        ▲ where it ACTUALLY goes            ▲ what the user SEES

    This is why "hover to check the link" is real advice — and why reading the raw HTML is better advice, because it also reveals the links a rendered view hides.

    Defang before you write it anywhere

    Never paste a live malicious URL into a ticket, a chat, or a report — someone will click it. Defang it first by breaking the clickable parts:

    Original:  http://www.suspiciousdomain.com
Defanged:  hxxp[://]www[.]suspiciousdomain[.]com

    Same for IPs (192[.]168[.]1[.]1) and email addresses (evil[at]domain[.]com). Defanging is a professional habit — an analyst who does not defang gets noticed for the wrong reason.

    Tracking pixels — the invisible header

    A 1×1 transparent image loaded from the attacker's server tells them the exact moment you opened the message, plus your IP and client. That is why mail providers block remote images by default, and why you should never open a suspicious email with images enabled — you would be confirming to the attacker that the mailbox is live and monitored.

    S07 · P09Security protocols⏱ 25 min

    Email Authentication — SPF, DKIM, DMARC

    Three DNS-based controls that together answer one question: is this sender allowed to use this domain? Reading their results correctly is the core Tier 1 skill of this session.

    SPF — Sender Policy Framework

    An SPF record is a DNS TXT record that lists the IP addresses and domains authorised to send mail for a domain. The receiving server looks it up and compares it to the actual sending IP.

    v=spf1 ip4:127.0.0.1 include:_spf.google.com -all
    PartMeaning
    v=spf1Start of the SPF record
    ip4:127.0.0.1This IPv4 address may send
    include:_spf.google.comEverything this domain authorises may also send
    -allHard fail — reject everything else

    SPF results — and what you do about each

    ResultMeaningIntended action
    NoneNo SPF record exists for the domainAccept
    PassThe IP is authorised (+)Accept
    NeutralThe owner explicitly takes no positionAccept
    SoftFailNot authorised, but do not reject (~all)Flag as suspicious
    FailThe IP is not authorised (-all)Reject
    TempErrorTemporary DNS/technical problemReject / retry
    PermErrorThe record has a syntax errorFlag
    SPF check — watch it run · pick a sender, then step through
    Sender
    Choose a sender above, then press Step ▶ to watch the receiving server run the check.

    DKIM — DomainKeys Identified Mail

    The sending server signs the message with a private key. The receiver fetches the matching public key from DNS and verifies the signature. If the signature checks out, the message genuinely came from that domain and has not been altered in transit.

    v=DKIM1; k=rsa; p=<public_key>
    ResultMeaning
    PassSigned and the signature verifies
    NeutralSigned, but the signature has syntax errors
    FailSigned but the signature does not verify
    PolicySigned, but the signature is not acceptable to the receiving domain
    TempErrorPublic key could not be retrieved
    PermErrorA required header field is missing
    DKIM check — watch it run · sign, send, verify
    In transit
    DKIM proves two things at once: who signed it and that nothing changed. Press Step ▶.

    DMARC — the policy layer

    DMARC adds the missing piece: alignment. SPF and DKIM can both pass for a domain the user never sees. DMARC insists that they line up with the visible From: — and tells the receiver what to do when they do not.

    v=DMARC1; p=quarantine; rua=mailto:postmaster@website.com
    PolicyWhat the receiver doesProtection
    p=noneDeliver normally, just reportMonitoring only
    p=quarantineDeliver to the spam/junk folderMedium
    p=rejectRefuse the message outrightStrongest

    rua= is where aggregate reports are sent — this is how a domain owner discovers who is spoofing them.

    DMARC decision — flip the switches · see why "pass" is not enough
    SPF
    DKIM
    Policy
    Try SPF: pass, not aligned with DKIM: fail — SPF says "pass", yet DMARC still fails. That gap is what attackers use.
    Reading the verdict as an analyst

    Find Authentication-Results: in the raw source and read all three together:

    • SPF Fail + DKIM Fail on a message claiming a well-known domain → high-confidence spoofing. Quarantine.
    • SPF SoftFail alone → suspicious; could also be legitimate forwarding. Keep looking.
    • All three Pass → the domain is real. That does not mean the email is safe — an attacker who registers paypal-security.com can configure perfect SPF/DKIM/DMARC for their own domain.

    The trap to internalise: authentication proves the sender owns the domain they claim. It never proves the domain is trustworthy. Look-alike domains pass authentication every day.

    S/MIME — the fourth control

    Where SPF/DKIM/DMARC protect the domain, S/MIME protects the individual message using public-key cryptography:

    Digital signature

    The sender signs with their private key; anyone can verify with the sender's public key.

    • Authentication — confirms the sender's identity via their certificate.
    • Non-repudiation — the sender cannot later deny sending it.
    • Data integrity — any change after signing is detected.
    Encryption

    The sender encrypts with the recipient's public key; only the recipient's private key can open it.

    • Confidentiality — only the intended recipient can read the content.

    Remember the pairing: sign with your private key, encrypt with their public key.

    ToolUse it for

    S07 · P10Theory⏱ 15 min

    Types of Phishing & the Red-Flag Checklist

    Name what you are looking at, then run the checklist. These are the last two things you learn before the break — and the first two you use after it.

    The family of email-borne attacks

    TypeIn one lineTarget
    SpamUnsolicited bulk mail. Malicious variety is called malspam.Everyone
    PhishingImpersonates a trusted entity to steal information.Mass, untargeted
    Spear phishingPersonalised using real details about the victim.One person or team
    WhalingSpear phishing aimed at executives (CEO, CFO).Senior leadership
    BEC (Business Email Compromise)Uses a genuinely compromised internal account to authorise fraud.Finance, HR, suppliers
    SmishingThe same attack delivered by SMS.Mobile users
    VishingVoice calls — social engineering over the phone.Anyone with a phone
    BEC is the expensive one — and the hardest to detect

    In a BEC the attacker is inside a legitimate mailbox. There is no spoofing: SPF, DKIM and DMARC all pass, because the mail genuinely comes from the real account. Your header analysis will look perfectly clean. The only signals are behavioural — an unusual payment request, a change of bank details, a new inbox forwarding rule, a login from a strange country. This is why we correlate email with authentication logs (P16) and never rely on headers alone.

    The red-flag checklist

    Nine indicators, in the order you check them:

    #Red flagWhat it looks like
    1Sender vs display name mismatch"Netflix Billing" <gibberish@sultanbogor.com>
    2Wrong or near-miss domainNumbers for letters, extra hyphens, wrong TLD
    3Unexpected attachmentFrom someone who has never sent you a file
    4Unusual attachment format.dot, .docm, .iso, .scr, double extensions like invoice.pdf.exe
    5Generic greeting"Dear Customer", "Dear User"
    6Too good to be trueLottery, prize, unexpected refund, dream job offer
    7Credential or action request"Log in to verify", "update your payment details"
    8Manufactured urgency"Within 24 hours", "your account will be closed"
    9Hidden or shortened linkDisplay text ≠ href; bit.ly masking the destination
    Where the old advice now fails

    "Look for spelling mistakes" used to be flag number one. With AI-written lures it is now close to useless — you will see flawless English, correct branding and accurate context. Flags 1, 2, 4 and 9 are the technical ones — they come from structure, not from language, and they still work. Weight them accordingly.

    Six real campaigns, six techniques

    Patterns you will meet again in the labs — each one a real sample:

    LureImpersonatesTechnique on show
    "Cancel your order"PayPalSpoofed sender + URL shortener hiding the destination
    "Track your package"Distribution centreLink manipulation + tracking pixel
    "Download document here"OneDrive → Adobe → OutlookMulti-stage redirect ending at credential harvest
    "Your account is on hold"NetflixMalicious URL hidden inside a PDF attachment
    "Your recent purchase"Apple SupportEmpty body + BCC recipient + .dot attachment
    "Scheduled shipment"DHL ExpressExcel attachment that downloads and runs an executable
    The pattern behind all six

    Every one of them does the same three things: borrow trust (a brand you know), create pressure (money, delivery, access), and ask for one click. Once you see that skeleton, the specific brand stops mattering — and you stop being surprised by new lures.

    Where email evidence lives — the log-source map

    Email log sources you should recognise anywhere
    • Linux (Postfix / sendmail) — /var/log/maillog, configured in /etc/syslog.conf. Grep by Message-ID, sender or recipient.
    • Microsoft Exchange — the ESE database (.edb for MAPI, .stm for non-MAPI) plus checkpoint and temp files. In practice you use Get-MessageTrackingLog in PowerShell, which is far more useful than the raw database for tracing delivery.

    • Network devices — router and firewall logs give times, IPs and Message-IDs for the servers involved.
    Safety rules for this session
    • Never open a suspicious attachment on your own workstation — only in the sandbox VM.
    • Never click a link from the message. Copy the URL, defang it, analyse it in a tool.
    • Block remote images before viewing anything — do not confirm the mailbox is live.
    • Everything you handle today is a lab artefact and stays inside the lab network.
    S07 · P12Tier 1⏱ 12 min

    Tier 1 — A User Reports an Email

    Your shift starts. Not with a SIEM alert this time — with a person.

    The ticket

    14:32 — Sara from Finance uses the Report Phishing button in Outlook. The message is auto-forwarded to soc@itgate.local, ingested by TheHive, and lands in your queue as an alert.

    "I got an invoice from a supplier I don't recognise. I didn't open the attachment but it looked odd, so I'm sending it to you."

    Where reported phish come from

    SourceWhat it tells you
    User report buttonA human found it suspicious — highest-value source, and it means the mail got past your filters
    Secure Email Gateway alertAutomated detection; the message may already be quarantined
    SIEM correlatione.g. a link click followed by a suspicious login
    Threat intel feedA campaign targeting your sector is already known
    Another victimA partner or supplier tells you they were compromised and you were mailed

    INE's Phishing Email Response Playbook — the canonical six steps — starts exactly here:

    1. Ingest the suspicious email alert via SIEM or mailbox monitoring.
    2. Automated analysis — check sender domain reputation, analyse headers and attachment hashes against threat intelligence, scan the body for malicious links.
    3. Containment — if confirmed malicious, quarantine the email from all mailboxes and block the sender domain.
    4. Notify the user — tell the recipient what it was and what to do.
    5. Update detection rules — add the new indicators so the next one is blocked.
    6. Document the incident — generate the report.
    First actions — before any analysis
    1. Acknowledge and assign. Take the alert in TheHive so nobody duplicates your work.
    2. Preserve the original. Get the .eml — the complete message with full headers. A forwarded screenshot is not evidence; a forwarded message loses the original headers. If the user only forwarded it inline, ask them to attach it instead, or pull it from the mail server.
    3. Ask the one question that changes everything: "Did you click anything, open the attachment, or enter your password?"
    4. Set an initial severity. Not clicked = investigate calmly. Clicked and credentials entered = this is now an active incident, escalate in parallel with your analysis.
    Why the answer to question 3 changes your whole day

    Not clicked → you have a prevented incident. Analyse, block, close. Clicked the link → check the proxy logs and assume the credential page was reached. Entered credentials → treat the account as compromised right now: reset the password, kill the active sessions, check for new inbox rules. Do not wait for your analysis to finish — an attacker can use stolen credentials within minutes.

Message-ID: <7f2a9c11-4b8e@supplier-invoices.top>
Content-Type: multipart/mixed; boundary="_004_INV2026"
    What this header block proves — line by line
    • Return-Path ≠ From. The envelope sender is mail-delivery-svc.top; the visible sender claims contoso-supplies.com. Two different domains.
    • Reply-To is a third domain. Replies would leave for mail-delivery-svc.top — the classic redirect.
    • Bottom Received: — the message originated from supplier-invoices.top at 203.0.113.77. That is a fourth domain, and the IP is the fact to pivot on.
    • spf=fail — that IP is not authorised to send for the claimed domain.
    • dkim=none — the message is not signed at all.
    • dmarc=fail action=quarantine — the receiving policy already flagged it.
    • Subject — "overdue" + "action required" = manufactured urgency (red flag 8).
    • .top TLD, three times. Cheap TLDs are heavily abused; three unrelated ones in one message is not a coincidence.

    Verdict from headers alone: phishing, high confidence. You have not even looked at the body yet.

    Say it the way a SOC writes it

    "Message received 06 Aug 14:28 from 203.0.113.77 (supplier-invoices.top), spoofing contoso-supplies.com. SPF fail, DKIM absent, DMARC fail/quarantine. Return-Path and Reply-To point to a third-party domain (mail-delivery-svc.top), consistent with credential or payment redirection. Assessed malicious — phishing."

    Short, factual, every claim tied to a header. That is the standard you are building toward.

    S07 · P14Tier 1⏱ 18 min

    Tier 1 — Links & Attachments

    The headers told you who. The body tells you what they wanted. Handle both without ever putting yourself at risk.

    Extracting the links

    1. Never click. Right-click → Copy link address, or read the href straight from the raw HTML.
    2. Defang immediately — hxxp[://]… — before it touches a ticket or a chat message.
    3. Expand shorteners. A bit.ly hides the destination; expand it with a redirect tracer such as WhereGoes rather than by visiting it.
    4. Compare display text to destination. A mismatch is red flag 9 and is often the whole case.
    5. Analyse the URL safely in URLScan.io — it browses the page for you and returns a screenshot, the redirect chain and the resources loaded, without you ever touching it.
    What a credential-harvest page looks like from the outside

    In URLScan you are looking for: a login form that imitates a known brand, a domain with no history (registered days ago), the form action posting to a different domain than the page itself, and often a redirect chain through two or three hops to defeat simple URL blocklists. The multi-stage pattern — OneDrive lookalike → Adobe lookalike → fake Outlook login — is textbook.

    Handling the attachment

    The safest route is the one you learned on P08: never download it from the mail client. Extract the base64 block from the raw source and rebuild the file in the sandbox VM.

    # In the sandbox VM only
sha256sum Invoice_INV-2026-0873.pdf
# 025ba9ce4a2118a9ca7b115c8869ff73bc16bad3732ba359cef1e60ad8f961f9

file Invoice_INV-2026-0873.pdf      # what it CLAIMS vs what it IS
xxd Invoice_INV-2026-0873.pdf | head -1
    The magic-number check — 10 seconds, catches disguises

    A file's real type is written in its first bytes, and the extension is just a label. If the header says MZ but the name ends in .pdf, you are holding a Windows executable wearing a costume:

    The triage decision

    Log the IOCs into the case

    Attach the observables to the TheHive case, mark them is IOC, and run the Cortex analysers — VirusTotal, URLhaus, AbuseIPDB, Whois/RDAP, MISP. The results come back into the case automatically, so the enrichment is recorded evidence rather than a browser tab you forget to screenshot.

    Blast radius — the question nobody should have to ask you

    Sara reported it. How many other people received it? Search the mail server by the artifacts you just logged — sender address, sending IP, subject line, attachment name. In our lab that is a Wazuh search over maillog:

    # every recipient of this campaign
rule.groups:postfix AND data.srcip:"203.0.113.77"

# by subject fingerprint
rule.groups:postfix AND data.subject:*INV-2026-0873*

# did anyone reach the phishing site?
rule.groups:fortigate AND data.url:*invoice-portal.top*

    That third query is the important one. A delivered email is a risk. A clicked link is an incident.

    The Tier 1 hand-off note

    Before you escalate, your case should already answer: What was it? Who sent it (IP + domain)? What did it want? Who received it? Did anyone click or open? What have I already blocked? If a Tier 2 responder has to ask you any of those, the hand-off was incomplete.

    S07 · P16Hand-off⏱ 10 min

    Escalate to Tier 2

    Knowing when to escalate is as much a skill as the analysis itself.

    Escalate when…
    • Someone clicked the link or opened the attachment.
    • Credentials were entered on the phishing page.
    • Endpoint telemetry shows execution after the email arrived.
    • The campaign hit many recipients or reached executives / finance.
    • You suspect BEC — a real internal account behaving oddly.
    • The mail requests a payment or bank-detail change.
    • Containment requires actions you do not have rights for — mailbox-wide purge, firewall block, account disable.
    Don't escalate when…
    • Ordinary bulk spam with no payload and no action requested.
    • Nobody interacted, the sender is already blocked, and there is no second recipient.
    • A confirmed false positive — a legitimate newsletter or supplier the user did not recognise.
    • An internal phishing simulation — verify with the security-awareness team before raising anything.

    Close these properly: document the verdict, block if useful, and thank the reporter. A user who gets thanked for a false alarm reports the real one next month.

    The correlation rule that makes this automatic

    INE's canonical multi-step example is exactly our scenario — and it is the single most valuable detection you can build for phishing:

    Correlation rule — phishing → credential use 
    Rule 1:  Detect phishing email delivery
Rule 2:  Detect unusual VPN / cloud login for the same user
Correlation: fire if BOTH occur within 30 minutes

    Neither rule alone is worth waking anyone for. Together they say: "the person who received the phishing email just logged in from somewhere new." That is a confirmed compromise, and it is a Tier 2 page-out, not a queue item.

    Tier 1 is not "the easy tier"

    Tier 2 will act on your summary, usually without re-reading the raw message. The quality of your hand-off is the quality of the response. A precise Tier 1 note is what makes a fast, correct containment possible.

    S07 · P17Tier 2⏱ 16 min

    Tier 2 — Contain the Campaign

    Containment for email is different from containment for malware: you are not isolating one host, you are removing a message from an entire organisation.

    The containment sequence

    1. Isolate the targeted system if there are signs of execution — the same EDR isolation you used in Session 6.
    2. Interview the users. Ask exactly what they did: downloaded the attachment, clicked the link, entered information, installed anything. Their answer scopes everything that follows.
    3. Purge the message from every mailbox — search by sender, subject and attachment name, then delete organisation-wide. This is the action that only Tier 2 usually has rights for, and it is the highest-value one.
    4. Block the infrastructure — sender address and domains at the mail gateway; the URL and its domain on the proxy; the sending IP at the firewall (in our lab, the FortiGate SOC_BLOCKLIST).
    5. Sandbox anything you have not yet detonated — links and attachments, in the isolated VM, to confirm behaviour and harvest more IOCs.
    6. Reset compromised credentials — and revoke active sessions. A password change alone does not kill a session token the attacker already holds.
    7. Notify the organisation. Tell everyone what to look for and what to do. This is also how you find the recipients who never reported it.
    8. Report to the provider — Gmail, Outlook and Yahoo all have a report path, and it helps their classifiers block the campaign for everyone.
    The step everyone forgets — inbox rules

    After a successful credential phish, the attacker's first action inside a mailbox is usually to create a forwarding or hiding rule: forward everything to an external address, or auto-move replies containing "invoice" or "payment" to a folder the user never opens. This is T1114.003 — Email Forwarding Rule.

    If you reset the password but leave the rule in place, the attacker keeps reading the mailbox. Always audit inbox rules and delegate permissions after any account compromise.

    Blast radius, properly measured

    QuestionWhere the answer lives
    Who received it?Mail server logs — search by sender IP / subject / attachment
    Who opened it?Mail gateway read receipts; tracking-pixel callbacks in proxy logs
    Who clicked?Proxy / FortiGate / DNS logs — the most reliable answer
    Who submitted credentials?Cannot be proven from your side — assume yes for anyone who clicked
    Whose account is being used?Authentication logs — impossible travel, new device, unusual hours
    Did anything execute?Sysmon EID 1, PowerShell 4104, EDR detections
    Communicate without causing a second incident

    When you send the organisation-wide notice, never paste the live URL and never forward the original message. Describe the lure — sender, subject, what it asks for — and tell people what to do: "do not click, report it, and if you already entered your password, contact the SOC immediately." Then make it easy to confess. The person who admits clicking gives you your timeline.

    The attachment detonated. From this moment on, you are running Session 6 — and now you know exactly how the malware got in.

    Everything so far has been email work. The instant a payload executes, the incident changes shape: it is now a malware incident with a known initial access vector.     S07 · P19Tier 2 · DF⏱ 20 min

    Email Forensics

    Preserve the evidence properly, then take the attachment apart. This is the forensics half of the session — and INE's canonical phishing case is exactly this.

    INE — Phishing Email Leading to Malware Infection

    Three forensic tasks, straight from the Digital Forensics module:

    1. Preserve the phishing email (headers, attachments).
    2. Extract indicators (malicious URL, hash of attachment).
    3. Analyse the infected host — dropped files, registry persistence keys, C2 communication in logs.

    Evidence sources and the question each one answers

    SourceCollectAnswers
    Mail serverOriginal .eml, message tracking logsWho — sender, spoofing, phishing origin
    Endpoint — memoryRAM captureWhat / how — running malware, injected processes
    Endpoint — diskForensic image (write blocker)How / impact — dropped files, persistence
    NetworkFirewall, proxy, IDS logsWhen / impact — C2 contact, exfiltration
    Where email fits in the order of volatility

    The order of volatility runs: CPU cache → RAM → network connections → disk → logs and backups. Email evidence sits at the low-volatility end because it lives on the server, not on the compromised host.

    The practical consequence: you do not have to choose. Capture RAM on the endpoint first, and collect the email evidence in parallel — a different system, a different responder, no conflict. What you must not do is let a mailbox retention policy expire while you work: preserve the message early even if you analyse it later.

    Preserving email evidence

    1. Export the original as .eml or .msg — never a screenshot, never a forward. A forward rewrites the headers and destroys the evidence.
    2. Hash it immediately — sha256sum message.eml — and record the value in the case.
    3. Document date, time, system, who collected it, and the tool used.
    4. Work only on copies. The original goes into evidence storage untouched.
    5. Log every transfer in the chain-of-custody form.
    Deleted-email recovery is time-limited

    If the user (or the attacker) deleted the message, you have a window — not forever:

    • Gmail — Trash retains for 30 days.
    • Outlook / Exchange — Recover Deleted Items From Server, default 14 days, configurable to 30.

    Recover it and immediately export as .eml or .msg before the retention window closes. An email you can no longer produce is an email that, legally, you never had.

    Analysing a malicious PDF

    PDFs are one of the most common phishing carriers. Attackers embed JavaScript inside PDF objects using tags like /JavaScript and /JS, triggered when the document opens, is clicked, or a form is used. Typical uses: exploit the reader, drop or download malware, or redirect to a fake form.

    # Quick triage — what dangerous features exist?
pdfid.py suspicious.pdf
#   looks for: /JavaScript  /JS  /OpenAction  /Launch

# Deep inspection — pull the JavaScript out and read it
pdf-parser.py -s /JavaScript suspicious.pdf

    /OpenAction means something runs the moment the file opens. /Launch means it tries to execute external content. Either in an "invoice" is damning on its own.

    Analysing a malicious Office macro

    Macro-enabled documents (.docm, .xlsm, and legacy .doc/.xls) remain one of the most common initial-access vectors. VBA macros can launch executables, run PowerShell, download further malware and establish persistence.

    olevba malicious.docm

    olevba (from the oletools suite) extracts the VBA, deobfuscates it, and flags the indicators that matter:

    • Auto-execution triggers — AutoOpen, Document_Open: the macro runs the moment the file is opened.
    • Suspicious keywords — Shell, CreateObject, WScript.Shell, calls to PowerShell or WMI.
    • Obfuscated strings — usually an encoded URL or payload, which becomes your next IOC.
    Lab exercise — the two resumes

    A classic scenario worth running exactly as written. You are a forensic examiner. David in HR received two resumes for an open position and viewed both. Days later the firewall administrator notices a strange outbound connection from David's machine. David is sure he opened no executables — only the two resumes. But he remembers one file popped up a "Save As" window, and when he cancelled, a second dialog asked him to click "Open" to view encrypted content. He does not remember which file it was; the names are similar. Examine both and report.

    Run pdfid on both, then pdf-parser -s /JavaScript on the one that flags. The /Launch action is the "Open" dialog David described.

    Locard's principle, applied to an inbox

    "Every contact leaves a trace." The email left a trace in the mail log. The click left a trace in the proxy log. The attachment left a trace in Sysmon. The payload left a trace in the registry. The C2 left a trace in the firewall. Your job is not to find evidence — it is to know where the traces already are.

    S07 · P20Tier 2⏱ 14 min

    Eradicate & Recover

    Remove the cause, immunise against the repeat, and get people working again.

    Eradication — technical

    1. Extract common patterns and signatures from the campaign and block them on the SMTP server — sender patterns, subject fingerprints, attachment names, URL patterns.
    2. DNS blackhole the domains and block the sending IPs.
    3. Blocklist the malicious sites and disable automatic downloads across all systems.
    4. Remove all malware artefacts from affected systems — the file, the persistence, the scheduled task.
    5. Block and re-issue compromised accounts — and remove any attacker-created inbox rules or delegate permissions.
    6. Deploy or tune anti-phishing tooling — gateway filtering, link rewriting, sandboxing, browser protections.

    Eradication — administrative

    • Report to anti-phishing bodies such as APWG (Anti-Phishing Working Group).
    • Use encryption or VPN for sensitive email communication.
    • Inform law enforcement where fraud or financial loss is involved.

    Recovery — in order

    #StepNote
    1Change passwords on affected accounts and anything relatedAlways first — and revoke sessions too
    2Notify banks / finance and block compromised accountsWhen payment fraud is involved
    3Restore compromised systems from backup or clean snapshotCLEAN-BASE in our lab
    4Contact law enforcementWhere required by policy or law
    5Insurance claim if losses are significantYour evidence pack matters here
    6File a complaint with the cybercrime authorityRegional process

    Steps 1–3 are technical recovery; 4–6 are legal and financial. As an analyst you own 1–3 and supply the evidence for 4–6.

    Prevention — what you recommend afterwards

    Technical controls
    • Email filtering — IP and domain reputation, block or quarantine.
    • Secure Email Gateway (SEG) — catches impersonation and spoofing other filters miss.
    • Link rewriting — replaces URLs with a checked redirect, so the destination is scanned at click time, not send time.
    • Sandboxing — detonates attachments and links in isolation before delivery.
    • SPF / DKIM / DMARC published for your own domain at p=reject, so nobody can spoof you.
    • MFA — the single control that most reduces the damage of a stolen password.
    People controls
    • Trust and warning banners — "External Sender", "Suspicious Link", first-time sender.
    • A one-click report button — make reporting easier than deleting.
    • Awareness training — attack types, social engineering, safe habits.
    • Phishing simulations — controlled campaigns to test and reinforce, used for training, never for punishment.
    • Out-of-band verification for payments and bank-detail changes — a phone call to a known number defeats BEC entirely.
    The seven layers of preparation

    A mature organisation has all seven: email filtering · email monitoring · an email-independent reporting channel (phone or chat, so a compromised mail system does not break your comms) · training · an acceptable use policy · archives and backups · email log analysis tooling. Items 1–2 are technical, 3–4 are people and process, 5 is governance, 6–7 are forensic readiness.

    Guided Lab — Operation Paper Trail

    The instructor runs a real phishing campaign from GoPhish against the lab mailboxes. You work the report exactly as you would on shift.

    Setup (instructor)

    GoPhish on KALI-ATK01 sends a fake supplier-invoice campaign to three lab mailboxes on LNX-VICTIM01 (Postfix/Dovecot). The lure carries a macro-enabled attachment and a link to a cloned login page hosted on the Kali box. One simulated user clicks; one opens the attachment on WIN-VICTIM01. Lab only — all infrastructure is inside the lab network and the payload is a benign simulation that cleans up at the end.

    1. Instructor launches the GoPhish campaign. Watch the maillog alerts arrive in Wazuh.
    2. Take the report. The TheHive alert appears from the reporting mailbox — assign it to yourself and open a case.
    3. Pull the raw source. Open the .eml in Thunderbird, Ctrl+U, and work the 12-artifact checklist from P13.
    4. Read the headers. Follow the Received: chain to the origin IP, check the auth results, compare From / Reply-To / Return-Path.
    5. Handle the payload safely. Extract the attachment from base64, hash it, run the magic-number check, and analyse it with olevba in the sandbox.
    6. Measure blast radius. Search maillog for every recipient; search FortiGate for anyone who reached the phishing site.
    7. Log the IOCs as observables in TheHive and run the Cortex analysers.
    8. Escalate with a complete hand-off note, then contain: purge, block, reset.
    9. Follow the payload on WIN-VICTIM01 — Sysmon process tree, C2 in FortiGate, persistence in the registry.
    10. Report. One page plus the MITRE table.

    ✅ What right looks like

    • You can name the origin IP from the bottom Received: line and say why it is more trustworthy than the From: address.
    • Your case has ≥ 6 observables, including the attachment SHA256 and the phishing URL, all defanged in the notes.
    • You can state the exact number of recipients and the exact number of clicks, each backed by a log query.
    • olevba output shows the auto-execution trigger and at least one suspicious keyword.
    • You can draw the process tree from Outlook to the payload from Sysmon evidence.
    • The message is purged from all mailboxes and the sender, domain and URL are blocked.
    The three things students most often miss

    1. Reading the Received: chain top-down instead of bottom-up. 2. Forgetting the blast-radius search — analysing only the one reported copy and missing the other thirteen recipients. 3. Resetting the password but never checking for the attacker's inbox forwarding rule.

    S07 · P23Challenge⏱ graded

    Challenge — Investigate Operation Paper Trail

    Answer every question from the evidence in the .eml, Wazuh, FortiGate and TheHive. Sequential — a wrong answer sends the next hunt to the wrong place.

    Case brief

    At 14:32 a Finance user reported a supplier invoice they did not recognise. By 15:10 the SOC had confirmed two clicks and one host beaconing outbound. Reconstruct the campaign from delivery to persistence, name the techniques, and recommend the response. Screenshot the evidence for every answer.

    Q1 Which single header value is the attacker unable to forge?

    • The From: address
    • The HELO/EHLO domain name
    • The source IP in the bottom Received: line
    • The Subject: line

    Q2 The headers show spf=fail and dkim=none. What does that combination tell you?

    • The message was encrypted in transit
    • The sender is not authorised for that domain and the message is unsigned — likely spoofed
    • The recipient's server is misconfigured
    • Nothing — these fail on normal mail all the time

    Q3 Which source proves that someone actually clicked the phishing link?

    • The mail server delivery log
    • Asking the user
    • The email gateway quarantine report
    • Proxy / firewall / DNS logs

    Q4 In Sysmon, which parent-child pair confirms the macro executed?

    • WINWORD.EXE → powershell.exe
    • explorer.exe → WINWORD.EXE
    • services.exe → svchost.exe
    • OUTLOOK.EXE → WINWORD.EXE

    Q5 The attachment is named Invoice.pdf but starts with bytes 4D 5A. What is it?

    • A corrupted PDF
    • A ZIP archive
    • A Windows executable disguised as a PDF
    • A JPEG image

    Q6 You reset the compromised user's password. What must you also check, or the attacker keeps access?

    • The user's browser bookmarks
    • Inbox forwarding rules and delegate permissions
    • The mail server's SPF record
    • The user's signature block

    Q7 Why is a BEC email so hard to catch with header analysis?

    • The headers are encrypted
    • BEC emails never contain headers
    • The attacker strips the Received: chain
    • It comes from a real compromised account, so authentication passes

    Q8 Which correlation rule turns two low-value alerts into a confirmed compromise?

    • Phishing delivery + unusual login for the same user within 30 minutes
    • Any email with an attachment
    • Two failed logins from one IP
    • A DNS query to a new domain

    The same incident is published as a three-dataset investigation case on the Investigation Case Files page — ingest the JSON into your own Splunk and answer 12 sequential questions from the evidence:

    paper-trail-mail.json      -> index=mail_logs     who received it
paper-trail-proxy.json     -> index=proxy_logs    who clicked, who submitted, the C2
paper-trail-endpoint.json  -> index=sysmon        what executed

    No single dataset answers the case — you have to correlate all three, exactly as you would on shift.
