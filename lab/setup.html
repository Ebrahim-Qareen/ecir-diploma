When it won't work

Part 0 · Host Prep (do once)

  • CPU 4+ cores with virtualization ON in BIOS (Intel VT-x / AMD SVM).
  • RAM 16 GB ideal (8 GB works — run fewer VMs at once). 150 GB+ SSD free.
  • Install VMware Workstation Pro (free).

On Windows 11, turn off Hyper-V for full speed, then reboot:

bcdedit /set hypervisorlaunchtype off

Part 2 · Splunk & Forwarders (Session 2)

Install Splunk on SOC-CORE01

sudo dpkg -i splunk-*.deb
sudo /opt/splunk/bin/splunk start --accept-license    # set admin user + password
sudo /opt/splunk/bin/splunk enable boot-start
sudo ufw allow 8000,9997/tcp

Open http://10.10.20.10:8000 from your host and log in.

Enable receiving + create indexes

sudo /opt/splunk/bin/splunk enable listen 9997 -auth admin:<pw>
sudo /opt/splunk/bin/splunk add index wineventlog
sudo /opt/splunk/bin/splunk add index linux

✅ Verify — then snapshot L2-splunk-ready

  • Web UI opens and you can log in
  • Settings → Indexes shows wineventlog and linux
  • Receive data shows port 9997 enabled

Forwarder — WIN-VICTIM01

Install the Windows UF (.msi) — set Receiving Indexer 10.10.20.10:9997, leave Deployment Server blank. Create these in ...\SplunkUniversalForwarder\etc\system\local\ (open Notepad as Administrator, and save as inputs.conf — not inputs.conf.txt):

inputs.conf — what to collect:

[WinEventLog://Security]
disabled = 0
index = wineventlog

[WinEventLog://System]
disabled = 0
index = wineventlog

[WinEventLog://Application]
disabled = 0
index = wineventlog

outputs.conf — where to send:

[tcpout]
defaultGroup = soc

[tcpout:soc]
server = 10.10.20.10:9997
Restart-Service SplunkForwarder

✅ Verify

  • Get-Service SplunkForwarder = Running
  • Splunk: index=wineventlog returns events
  • Log off/on → a new 4624 appears

Forwarder — LNX-VICTIM01

sudo dpkg -i splunkforwarder-*.deb
sudo /opt/splunkforwarder/bin/splunk start --accept-license --run-as-root
sudo /opt/splunkforwarder/bin/splunk add forward-server 10.10.20.10:9997 -auth admin:<pw>
sudo /opt/splunkforwarder/bin/splunk add monitor /var/log/auth.log -index linux
sudo /opt/splunkforwarder/bin/splunk add monitor /var/log/syslog  -index linux
sudo /opt/splunkforwarder/bin/splunk restart

✅ Verify — then snapshot L2-complete

  • index=linux returns events
  • Wrong SSH password → "Failed password" appears in Splunk

First searches

index=wineventlog EventCode=4624 | stats count by Account_Name
index=wineventlog EventCode=4625 | table _time, Account_Name, Source_Network_Address
index=linux "Failed password" | stats count by host

Part 3 · Sysmon & auditd — Deep Telemetry (Session 3)

Session 2 gave you native logs. Part 3 adds the deep endpoint telemetry an analyst actually hunts in: Sysmon on Windows and auditd on Linux. Snapshot both victims first (pre-sysmon).

New indexes on SOC-CORE01

sudo /opt/splunk/bin/splunk add index sysmon
sudo /opt/splunk/bin/splunk add index linux_audit

Sysmon on WIN-VICTIM01

Download Sysmon (Sysinternals) and a config — the community standard is sysmonconfig.xml (SwiftOnSecurity) or Olaf Hartong's modular config. In an admin PowerShell:

.\Sysmon64.exe -accepteula -i sysmonconfig.xml
Get-Service Sysmon64          # should be Running

Add the Sysmon channel to the forwarder's ...\SplunkUniversalForwarder\etc\system\local\inputs.conf:

[WinEventLog://Microsoft-Windows-Sysmon/Operational]
disabled = 0
index = sysmon
renderXml = false
Restart-Service SplunkForwarder

✅ Verify — then snapshot sysmon-ready

  • index=sysmon returns events
  • Open Notepad → a Sysmon EventID=1 appears with a full CommandLine and Hashes
  • Open a browser → index=sysmon EventID=3 shows a network connection

auditd on LNX-VICTIM01

sudo apt-get install -y auditd
# watch process execution and identity files
sudo auditctl -a always,exit -F arch=b64 -S execve -k proc
sudo auditctl -w /etc/passwd -p wa -k identity
# forward the audit log
sudo /opt/splunkforwarder/bin/splunk add monitor /var/log/audit/audit.log -index linux_audit
sudo /opt/splunkforwarder/bin/splunk restart

✅ Verify — then snapshot L3-telemetry-ready

  • index=linux_audit returns execve events after you run a command
  • Editing a user (sudo useradd test1) triggers an identity-keyed event

First deep-telemetry searches

index=sysmon EventID=1 | stats count by ParentImage | sort -count
index=sysmon EventID=1 ParentImage="*WINWORD*" | table _time, Image, CommandLine
index=sysmon EventID=3 | stats count by Image, dest_ip, dest_port
index=linux_audit event_type=execve user=root | table _time, process, command

Part 4 · Wazuh SIEM/XDR (Lab Extension)

Splunk gives you a hand-built SIEM pipeline — you control every index, forwarder, and search. Wazuh adds a production-grade open-source XDR agent that does FIM, vulnerability detection, SCA (CIS benchmarks), active response, and ships with a ruleset already mapped to MITRE ATT&CK. You now see both worlds — exactly what real SOCs run.

Requirements

AgentsCPURAMStorage (90 days)
1–254 vCPU8 GiB50 GB

SOC-CORE01 already meets this. OS must be 64-bit Linux (Ubuntu 20.04/22.04/24.04, RHEL 8/9). The VM needs outbound internet to packages.wazuh.com during install.

Install Wazuh all-in-one on SOC-CORE01

This installs the indexer, server, and dashboard on a single host:

curl -sO https://packages.wazuh.com/4.14/wazuh-install.sh && sudo bash ./wazuh-install.sh -a

Takes 5–15 minutes. When it finishes:

INFO: --- Summary ---
INFO: You can access the web interface https://<WAZUH_DASHBOARD_IP>
    User: admin
    Password: <ADMIN_PASSWORD>
INFO: Installation finished.

Copy that password now — it appears once. To recover later:

sudo tar -O -xvf wazuh-install-files.tar wazuh-install-files/wazuh-passwords.txt
Credential hygiene

wazuh-install-files.tar contains plaintext credentials. Keep it on the lab VM only — never commit it to a repo or upload it anywhere. Same rule as the Splunk lab credentials.

Access the dashboard

Open https://10.10.20.10 → login admin / the password from above. The browser warns the certificate is not trusted — expected (self-signed). Accept the exception.

Disable auto-updates

Prevents an unattended upgrade from breaking the lab mid-course:

# Debian/Ubuntu
sudo sed -i "s/^enabled=1/enabled=0/" /etc/apt/sources.list.d/wazuh.list 2>/dev/null
# RHEL/CentOS
sudo sed -i "s/^enabled=1/enabled=0/" /etc/yum.repos.d/wazuh.repo

Stop Splunk (free up resources)

Wazuh's indexer (OpenSearch) is memory-hungry. If you're tight on RAM, stop Splunk while working with Wazuh:

sudo /opt/splunk/bin/splunk stop
# optional: wipe old data to reclaim disk
sudo /opt/splunk/bin/splunk clean all -f

✅ Verify — then snapshot L4-wazuh-installed

  • sudo systemctl status wazuh-manager wazuh-indexer wazuh-dashboard — all three active (running)
  • Dashboard loads at https://10.10.20.10 and you can log in

Deploy agent — LNX-VICTIM01

On LNX-VICTIM01:

wget https://packages.wazuh.com/4.x/apt/pool/main/w/wazuh-agent/wazuh-agent_4.14.6-1_amd64.deb
sudo WAZUH_MANAGER='10.10.20.10' WAZUH_AGENT_NAME='soc-linux-victim01' dpkg -i ./wazuh-agent_4.14.6-1_amd64.deb
sudo systemctl daemon-reload
sudo systemctl enable wazuh-agent
sudo systemctl start wazuh-agent

Deploy agent — WIN-VICTIM01

In an Administrator PowerShell on WIN-VICTIM01:

Invoke-WebRequest -Uri https://packages.wazuh.com/4.x/windows/wazuh-agent-4.14.6-1.msi -OutFile $env:tmp\wazuh-agent.msi
msiexec.exe /i $env:tmp\wazuh-agent.msi /q WAZUH_MANAGER='10.10.20.10' WAZUH_AGENT_NAME='soc-win-victim01'

✅ Verify — then snapshot L4-agents-enrolled

  • Dashboard → Agents management: both soc-linux-victim01 and soc-win-victim01 show Active (green)
  • sudo systemctl status wazuh-agent on LNX-VICTIM01 = active (running)
  • Get-Service WazuhSvc on WIN-VICTIM01 = Running

Configure Windows agent — collect Security, Sysmon, PowerShell, Task Scheduler

Run in an Administrator PowerShell on WIN-VICTIM01:

Stop-Service WazuhSvc
$conf = "C:\Program Files (x86)\ossec-agent\ossec.conf"
Copy-Item $conf "$conf.bak"
[xml]$xml = Get-Content $conf

# Remove old entries to avoid duplicates
$targets = @("Security","Microsoft-Windows-Sysmon/Operational","Microsoft-Windows-PowerShell/Operational","Microsoft-Windows-TaskScheduler/Operational")
$xml.ossec_config.localfile | Where-Object { $targets -contains $_.location } |
    ForEach-Object { $xml.ossec_config.RemoveChild($_) }

foreach ($loc in $targets) {
    $lf = $xml.CreateElement("localfile")
    $lf.InnerXml = "<location>$loc</location><log_format>eventchannel</log_format>"
    $xml.ossec_config.AppendChild($lf) | Out-Null
}

$xml.Save($conf)
Start-Service WazuhSvc
Get-Service WazuhSvc

This forwards: all Security events, Sysmon (process/network/file), PowerShell script block logging (enable via GPO first — T1059.001), and Task Scheduler (persistence — T1053.005).

Configure Linux agent — auth.log + nginx JSON logs

First, install nginx and configure JSON logging on LNX-VICTIM01:

sudo apt update && sudo apt install -y nginx
sudo systemctl enable nginx && sudo systemctl start nginx
sudo tee /etc/nginx/conf.d/json_log.conf > /dev/null <<'EOF'
log_format json_combined escape=json
  '{'
    '"srcip":"$remote_addr",'
    '"time":"$time_local",'
    '"method":"$request_method",'
    '"url":"$request_uri",'
    '"status":$status,'
    '"size":$body_bytes_sent,'
    '"referer":"$http_referer",'
    '"user_agent":"$http_user_agent"'
  '}';

access_log /var/log/nginx/access-json.log json_combined;
EOF
sudo nginx -t && sudo systemctl reload nginx

Then add log sources to the Wazuh agent config (/var/ossec/etc/ossec.conf):

sudo sed -i '/<\/ossec_config>/i \
  <localfile>\
    <log_format>syslog</log_format>\
    <location>/var/log/auth.log</location>\
  </localfile>\
  <localfile>\
    <log_format>json</log_format>\
    <location>/var/log/nginx/access-json.log</location>\
  </localfile>' /var/ossec/etc/ossec.conf

sudo systemctl restart wazuh-agent

Nginx logs arrive as structured JSON — every field (srcip, method, url, status, user_agent) is automatically searchable in the dashboard. No custom decoder needed.

Custom decoders — SSH field extraction

On SOC-CORE01 (the manager), add child decoders to extract SSH and nginx UA fields:

sudo tee /var/ossec/etc/decoders/local_decoder.xml > /dev/null <<'EOF'
<decoder name="sshd-custom">
  <program_name>^sshd</program_name>
</decoder>

<decoder name="sshd-failed-password">
  <parent>sshd-custom</parent>
  <prematch>Failed password</prematch>
  <regex offset="after_prematch">for (\S+) from (\S+) port (\d+)</regex>
  <order>dstuser, srcip, srcport</order>
</decoder>

<decoder name="sshd-accepted">
  <parent>sshd-custom</parent>
  <prematch>Accepted \S+ for</prematch>
  <regex offset="after_prematch">for (\S+) from (\S+) port (\d+)</regex>
  <order>dstuser, srcip, srcport</order>
</decoder>

<decoder name="web-accesslog-ua">
  <parent>web-accesslog</parent>
  <prematch type="pcre2">HTTP/\d.\d"</prematch>
  <regex type="pcre2" offset="after_prematch"> (\d+) \d+ "([^"]*)" "([^"]*)"$</regex>
  <order>id, referer, user_agent</order>
</decoder>
EOF
sudo /var/ossec/bin/wazuh-control restart

✅ Verify — then snapshot L4-wazuh-complete

  • Dashboard → Threat Hunting: filter by soc-linux-victim01 — curl http://localhost on the victim generates an nginx event with data.srcip, data.url, data.user_agent fields
  • Intentional failed SSH → alert with srcip, dstuser, MITRE T1110.001 mapped
  • Filter by soc-win-victim01 → Security + Sysmon + PowerShell events flowing
  • sudo /var/ossec/bin/wazuh-logtest — paste a sample log, confirm fields extract cleanly

Troubleshooting — real gotchas from the build

Every one of these actually happened building this lab. Match the symptom, apply the fix.

SymptomCause → Fix
Victim can't ping the SOC serverTwo host-only nets don't route → put all lab adapters on the same VMnet10; allow ICMP on Windows Firewall
Invalid YAML: inconsistent indentationNetplan is space-sensitive → 2-space indent, block is ethernets: (not ethernet:)
netplan "permissions … too open"sudo chmod 600 /etc/netplan/00-installer-config.yaml
"Oh no! Something has gone wrong" (GNOME)You installed Ubuntu Desktop → reinstall with the Server ISO
Splunk prints a deprecation warning, won't startRunning as root → add --run-as-root
splunk.service: Failed … exit-code on bootUnit assumes non-root → splunk enable boot-start -user root, then systemctl daemon-reload
Forwarder: "target machine actively refused it" (9997)Splunk down or 9997 not listening → start Splunk, splunk enable listen 9997, check ss -tlnp | grep 9997
"Received event for unconfigured/disabled/deleted index"Index missing after a rebuild → recreate splunk add index wineventlog / linux
Restart-Service … cannot open servicePowerShell not elevated → run it as Administrator
VMware "not enough space" / NAT broken / can't reach internetHost C: drive full → free space, keep VMs off C:/OneDrive, ensure VMware NAT Service is running
Web UI won't opensplunk status; sudo ufw allow 8000/tcp
VMware slowHyper-V still on — see Part 0
No index=sysmon dataSysmon running? exact channel in inputs.conf? forwarder restarted? sysmon index created?
auditd rules reset on rebootPut rules in /etc/audit/rules.d/soc.rules so they persist
Wazuh install hangs or failsNot enough RAM (need 8 GB) or no internet to packages.wazuh.com — check free -h and curl -I https://packages.wazuh.com
Wazuh agent stays Never connectedFirewall blocking port 1514/1515 → sudo ufw allow 1514,1515/tcp on SOC-CORE01; or wrong manager IP in agent config
Wazuh decoder error 1113 / XML syntaxDon't use the dashboard uploader for local_decoder.xml — edit via nano on the CLI. Use sudo tee ... <<'EOF' to avoid shell quote mangling
NET START Wazuh fails on WindowsService name is WazuhSvc, not Wazuh → NET START WazuhSvc
No nginx events in Wazuh dashboardCheck /var/log/nginx/access-json.log exists and has data; verify log_format json in agent's ossec.conf
